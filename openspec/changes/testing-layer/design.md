## Goals

- Определить единый слой тестирования, ориентированный на OpenSpec specs.
- Обеспечить трассируемость: для каждого spec есть связанный набор тестов.
- Ввести «правило change»: любой новый change включает задачи на тестирование и интеграцию в слой.
- Поддержать сценарии, требующие credentials, без утечки секретов в репозиторий.
- Сделать запуск тестов простым: единые команды, режимы (быстро/полно), выборка по spec.

## Non-goals

- Замена текущего стека сборки/запуска или переход на другой тест-раннер.
- Переписывание существующих unit/integration/e2e тестов, если они уже есть и работают.
- Гарантия 100% покрытия кода — цель про покрытие требований/сценариев OpenSpec.

## Approach

### 1) Структура тестов «по спекам»

Договориться о директории и соглашении именования, чтобы:

- тесты группировались по `openspec/specs/<capability>/...`;
- было легко найти: «какие тесты покрывают этот spec».

Пример (черновой вариант, уточнить в реализации):

- `test/specs/<capability>/**/*.spec.ts` — тесты по спекам;
- `test/fixtures/**` — детерминированные фикстуры и генераторы данных;
- `test/helpers/**` — общие утилиты.

### 2) Traceability: ссылка тест ↔ spec

Выбрать один из вариантов (зафиксировать окончательно в реализации):

- (предпочтительно) фронтматтер/комментарий в тесте с путём до spec-файла;
- или индекс-файл (map) `test/specs/index.json`, собираемый скриптом.

Критерий: проверяемость (линтер/скрипт, который валидирует, что для всех specs есть тесты).

### 3) Минимальная планка покрытия

- для каждого spec: минимум один тест на каждый ключевой scenario из документа;
- для «критичных» доменов (auth/access-control/llm-endpoint и т.п.) — отдельные smoke-тесты.

### 4) Credentials и mock-данные

- credentials предоставляются через переменные окружения (локально — `.env.local`, в CI — секреты окружения).
- если credentials не доступны, тесты должны уметь работать в режиме mock (где это допустимо).
- фикстуры должны быть детерминированными; генерация данных — воспроизводимой.

### 5) Команды запуска

Нужны, как минимум:

- быстрый запуск слоя (smoke) — проверка основного;
- полный запуск слоя;
- запуск по capability/spec.

Команды (черново) фиксируются в инструкции и закрепляются в `package.json` на этапе реализации.

## Risks / Tradeoffs

- Связь «спек ↔ тесты» может стать бюрократией, если формат будет слишком тяжёлым.
- Некоторые сценарии OpenSpec могут требовать UI/e2e прогонов и будут дольше выполняться.
- Credentials-зависимые тесты могут быть нестабильны без строгих правил таймаутов и ретраев.

## Open Questions

- Какой источник правды для покрытия: сценарии в spec-файлах или отдельный coverage-index?
- Нужна ли отдельная маркировка тестов по уровням (unit/integration/e2e) внутри слоя?
- Какие внешние интеграции реально нужны для покрытия существующих specs, и где достаточно mock?
