## Context

Сейчас runtime preview уже умеет ловить часть ошибок на этапе загрузки модуля: сетевую ошибку, неуспешный ответ API, отсутствие default-экспорта и исключения во время подготовки модуля через `new Function`. Но у React-рендера пользовательского компонента отдельный failure mode: компонент может выбросить ошибку уже после того, как был успешно загружен и смонтирован.

В таком сценарии пользователю не нужен глобальный crash страницы. Ему нужен локальный, понятный fallback внутри preview-области, после которого остальной task-screen, кодовая панель и системная навигация остаются живыми.

## Goals / Non-Goals

**Goals:**
- Защитить preview пользовательского компонента от runtime-ошибок React-рендера.
- Свести область падения к одному render-островку вместо всей страницы.
- Показывать понятное локальное сообщение об ошибке вместо пустого блока или crash.
- По возможности распространить этот паттерн на остальные shell-островки, где boundary добавляется почти бесплатно и изолирует нестабильный рендер.

**Non-Goals:**
- Лечить сам пользовательский код автоматически.
- Подменять ошибку молчаливым успешным рендером.
- Оборачивать без разбора весь проект в тяжёлый глобальный слой, если это усложняет архитектуру и маскирует реальные product-shell ошибки.

## Decisions

### 1. Preview пользовательского компонента получает обязательный локальный boundary

Все точки task-preview, где система рендерит пользовательский компонент из runtime-модуля, должны иметь локальную защиту, которая перехватывает ошибки React-рендера и заменяет компонент на понятное сообщение об ошибке.

Альтернатива: полагаться только на try/catch вокруг загрузки модуля.
Почему не она: try/catch перед рендером не ловит ошибки, которые происходят уже внутри дерева React-компонента.

### 2. Ошибка ограничивается preview-островком, а не страницей

При падении пользовательского компонента система должна сохранять работоспособность окружающего task-screen: редактор, навигация, статусные блоки и прочий shell не должны исчезать вместе с preview.

Альтернатива: использовать только route-level error handling.
Почему не она: route-level обработчик слишком грубый и перехватывает больше UI, чем нужно для локальной ошибки пользовательского кода.

### 3. Расширение на другие shell-компоненты делается по принципу low-cost/high-value

Если в product-shell уже есть render-островки с повышенным риском или сторонним/динамическим содержимым, и boundary можно добавить почти бесплатно без заметной архитектурной цены, такой паттерн следует распространить и туда. Но это не означает слепое оборачивание каждого статического компонента.

Альтернатива: обязать boundary буквально для каждого компонента проекта.
Почему не она: это создаёт механическую и шумную обвязку там, где дополнительной ценности почти нет.

## Risks / Trade-offs

- [Слишком широкий scope] → можно начать оборачивать boundary там, где он не нужен → смягчается правилом “low-cost/high-value” и фокусом на рискованные render-островки.
- [Скрытие полезных ошибок] → fallback может замаскировать инженерный сигнал → смягчается тем, что сообщение остаётся явным и не притворяется успешным рендером.
- [Разные типы ошибок] → часть ошибок возникает до React-рендера, часть внутри него → решение должно покрыть оба пути, а не заменить один другим.
