## Context

Контур допуска состоит из двух логик:
- marker-check по email (`/api/access/verify`);
- вычисление текущего состояния сессии допуска (cookie + TTL) для статуса системы.

Из-за различий ответа хостинга на `HEAD` и `GET` marker-check мог вернуть отказ при реально существующем маркере. В результате пользователь видел ошибку допуска, хотя системный статус мог оставаться `valid` из-за уже существующей сессии.

## Goals / Non-Goals

**Goals:**
- Убрать ложный отказ допуска при `HEAD 404` + `GET 200`.
- Сохранить корректный отказ при реальном отсутствии маркера (`GET 404`).
- Унифицировать env-ключи в коде и интерфейсе вокруг `DESENGINE_*`.

**Non-Goals:**
- Изменять модель marker-based allowlist.
- Менять TTL сессии допуска или cookie-формат.
- Вводить новый backend вместо статического allowlist-хранилища.

## Decisions

### 1) Marker-check должен подтверждаться GET при любом `HEAD != 200`

Если `HEAD` по marker URL не дал `200`, система обязана сделать `GET` и принимать его как окончательный ответ.

Это покрывает хостинги, где `HEAD` не поддержан корректно или даёт другой ответ, чем `GET`.

### 2) Контракты env-имен фиксируются на `DESENGINE_*`

Основные runtime-ключи и пользовательские тексты приводятся к:
- `DESENGINE_ALLOWLIST_BASE_URL`
- `DESENGINE_ALLOWLIST_SALT`
- `DESENGINE_ONBOARDING_REPO_URL`

Для обратной совместимости чтение legacy-имен допускается как fallback там, где это безопасно.

## Risks / Trade-offs

- [Дополнительный GET] → небольшое увеличение сетевых обращений в marker-check → приемлемо ради корректности допуска.
- [Смешанные legacy-конфиги] → возможны неоднозначности при одновременном наличии старых и новых ключей → mitigated через приоритет `DESENGINE_*`.
