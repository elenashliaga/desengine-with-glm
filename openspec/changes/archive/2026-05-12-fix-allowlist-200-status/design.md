## Context

Сейчас в проекте смешаны два разных контракта:
- проверка конкретного allowlist-маркера по email, где `404` естественно означает “этого email нет в списке допуска”;
- проверка доступности самой allowlist-системы по базовому URL, где `404` сейчас тоже считается допустимым.

Именно второе поведение создаёт баг. Базовый URL системы не должен в штатном состоянии выглядеть как “не найдено”, потому что это ломает диагностическую ясность и маскирует ошибки развёртывания.

## Goals / Non-Goals

**Goals:**
- Зафиксировать явный контракт: базовый URL allowlist-системы в штатном состоянии отвечает `200`.
- Развести семантику system-check и marker-check, чтобы `404` оставался допустимым только для отсутствующего email-маркера.
- Сделать диагностику готовности allowlist однозначной и пригодной для автоматических проверок.

**Non-Goals:**
- Менять схему marker-based allowlist-проверки по email.
- Менять формат allowlist-хранилища, salt-маркеров или пользовательский flow допуска.
- Добавлять новый backend-сервис вместо существующего статического или удалённого размещения.

## Decisions

### 1. Базовый URL allowlist-системы получает отдельный health-контракт

Проверка доступности allowlist-системы должна ожидать `200` на базовом URL, заданном в `ALLOWLIST_BASE_URL`. Ответ `404` больше не считается “система доступна, всё нормально”.

Альтернатива: продолжать считать `404` допустимым, если marker URLs работают.
Почему не она: это сохраняет неясный и хрупкий контракт, в котором системная точка проверки неотличима от ошибочного маршрута.

### 2. Marker-check по email сохраняет текущую семантику

Проверка конкретного email-маркера остаётся отдельным потоком: `200` означает допуск, `404` означает отсутствие допуска, другие ответы означают техническую проблему.

Альтернатива: запретить `404` вообще в allowlist-контуре.
Почему не она: это сломает саму модель статических маркеров, где отсутствие файла и есть отказ в допуске.

### 3. Диагностика должна различать “система недоступна” и “email не найден”

UI- и server-side диагностика не должны смешивать ответ базового URL системы с ответом конкретного marker URL. Для статуса готовности allowlist используется system-check с ожиданием `200`; для пользовательского допуска используется marker-check с прежней семантикой.

## Risks / Trade-offs

- [Более строгий health-контракт] → существующие allowlist-развёртывания с `404` на корне перестанут считаться корректными → это осознанный breaking-fix для диагностики, который нужно покрыть документацией.
- [Два похожих сетевых сценария] → можно случайно снова смешать system-check и marker-check в коде → смягчается отдельными проверками и явной терминологией в spec.
- [Статический хостинг] → для части хостингов может понадобиться добавить index/health-файл или перенастроить rewrite, чтобы корень отвечал `200`.
