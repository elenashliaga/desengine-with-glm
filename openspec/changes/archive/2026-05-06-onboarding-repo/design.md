## Context

В текущем состоянии продукта onboarding-слой распределён по нескольким внутренним каталогам:
- `levels/**` хранит конфиги уровней, их `overview` и `init-prompt`;
- `tasks/**` хранит task config и reference assets вроде `base.png` / `variants.png`;
- `prompts/didactic/**` хранит didactic-промпты;
- `prompts/production/**` хранит production-промпты runtime-логики.

Для пользователя и команды это уже выглядит как отдельная подсистема контента, но технически она живёт в основном репозитории вместе с кодом продукта. Ранее это уже обсуждалось в change `externalize-didactics-repo`, но тот change фиксировал более раннюю и более узкую модель:
- там речь шла про didactics-repo;
- механизм подключения ещё сознательно не уточнялся;
- состав выносимого слоя был менее конкретным.

Текущая постановка точнее:
- нужен не просто “репозиторий дидактики”, а единый внешний onboarding-слой;
- этот слой должен монтироваться/подгружаться в продукт как `/onboarding`;
- адрес репозитория onboarding-контента должен задаваться через уже существующий `config.txt` переменной `ONBOARDING_REPO_URL`;
- в него входят уровни, только `config.json`, `base.png`, `variants.png` из `tasks/**`, а также didactic-промпты;
- production-prompts остаются в основном репозитории;
- в этой фазе продукт должен читать onboarding-слой только из `/onboarding` без fallback к старым корневым каталогам;
- для `/onboarding` в контракте остаётся только ручное обновление по кнопке на `/config`;
- если `/onboarding` недоступен, система пока не падает насмерть, а запускается с явным статусом проблемы.

## Goals / Non-Goals

**Goals:**
- Зафиксировать единый onboarding-контент как внешний источник правды.
- Развести onboarding-контент и runtime-код по разным репозиториям ответственности.
- Явно определить, какие данные уходят во внешний `/onboarding`, а какие остаются в основном репозитории.
- Зафиксировать ручное обновление onboarding-контента через `/config`.
- Зафиксировать штатное поведение системы при временной недоступности `/onboarding`.

**Non-Goals:**
- Выбор конкретного механизма подключения внешнего репозитория.
- Немедленная реализация миграции всех файлов.
- Переезд `prompts/production/**` во внешний контентный репозиторий.
- Детализация CI/CD, auth и release-процесса для onboarding-репозитория.

## Decisions

- Внешний onboarding-контент собирается под единым корнем `/onboarding`.
  - `/onboarding` — это не просто папка, а отдельный контентный слой продукта.
  - Канонический источник этого слоя — отдельный репозиторий.

- URL onboarding-репозитория задаётся в `config.txt` через `ONBOARDING_REPO_URL`.
  - Продукт не должен хардкодить адрес внешнего onboarding-репозитория в коде.
  - Конфигурация подключения onboarding-контента становится частью локального конфигурационного файла системы.

- В onboarding-репозиторий входят:
  - уровни (`levels/**`);
  - только `config.json` из `tasks/**`;
  - только базовые task reference assets (`base.png`, `variants.png`);
  - `prompts/didactic/**`.

- Старые рабочие исходники и история не входят в onboarding-репозиторий.
  - `Component.tsx`, `Component.stories.*`, `styles.ts`, `mock.ts`, `props.ts`, `prompt-history.json` не считаются частью versioned onboarding-контента.
  - Их наличие в `tasks/**` трактуется как legacy-мусор, который должен быть удалён.

- `prompts/production/**` остаются в основном репозитории.
  - Production-промпты относятся к runtime-логике продукта и имеют отдельную судьбу.
  - Они не считаются частью onboarding-репозитория в этом change.

- Основной репозиторий остаётся хозяином:
  - runtime-кода;
  - доступа, конфигурации, локального запуска;
  - LLM-интеграции;
  - production-prompts;
  - технической документации и инфраструктуры продукта.

- Onboarding-репозиторий становится хозяином:
  - уровней;
  - task onboarding-конфигов;
  - базовых task reference assets;
  - didactic-промптов;
  - связанных onboarding-материалов, если они напрямую относятся к образовательному слою.

- В этой фазе `/onboarding` обязателен без fallback.
  - Если продукту нужны onboarding-данные, он читает их только из `/onboarding`.
  - Старые корневые `levels/**`, `tasks/**`, `prompts/didactic/**` не используются как тихий запасной источник.

- Для `/onboarding` остаётся только ручное обновление с `/config`.
  - Контракт не фиксирует автоматическое удаление `/onboarding`, фоновый lifecycle или связь с пользовательским допуском.
  - Единственная явная точка обновления onboarding-контента — пользовательское действие `Обновить onboarding` на `/config`.

- Недоступность `/onboarding` пока не убивает весь запуск.
  - Если onboarding-контент не подгрузился, система должна запускаться.
  - При этом она должна явно показывать статус или ошибку, что onboarding-контент недоступен.
  - Это временная рабочая модель на текущем этапе.

- Этот change логически заменяет `externalize-didactics-repo`.
  - Из старого change нужно сохранить полезные идеи о внешнем источнике правды и разделении ответственности.
  - Но итоговый контракт должен быть один: про onboarding-репозиторий, а не про более расплывчатый didactics-repo.

## Risks / Trade-offs

- [Два репозитория] → координация между кодом и onboarding-контентом усложняется → это допустимо, если границы владения и ручной update-контракт зафиксированы явно.
- [URL репозитория в config.txt] → ошибка конфигурации может сделать onboarding недоступным → это допустимо, если система явно показывает статус проблемы на `/config` и в общем статусе.
- [Система запускается без `/onboarding`] → продукт может оказаться частично работоспособным, но без основного контента → поэтому нужен явный статус недоступности, а не тихий fallback.
- [Обязательный `/onboarding` без fallback] → локальная установка будет жёстче реагировать на неполную миграцию → это допустимо, потому что команда сознательно не хочет застревать в переходном режиме.
- [Замена старого change новым] → можно оставить два конкурирующих контракта в OpenSpec → нужно явно зафиксировать, что итоговый контракт должен остаться один.

## Pre-Implementation Checklist

- Сопоставить существующие каталоги `levels/**`, `tasks/**`, `prompts/didactic/**`, `prompts/production/**` с новой моделью `/onboarding`.
- Зафиксировать имя `ONBOARDING_REPO_URL` и его роль в `config.txt`.
- Для `tasks/**` отделить onboarding-owned содержимое (`config.json`, `base.png`, `variants.png`) от runtime/user-owned артефактов.
- Проверить пересечение с уже существующими change:
  - `externalize-didactics-repo`
  - `user-state-separation`
  - `flatten-lab-into-root` и смежные layout-change, если они влияют на пути
- Зафиксировать, какие статусы и диагностические сигналы должна показывать система при отсутствии `/onboarding`.
- Зафиксировать, что для `/onboarding` в change остаётся только ручное действие `Обновить onboarding` на `/config`.
- Подготовить план консолидации OpenSpec, чтобы после этого change не осталось двух конкурирующих контрактов про внешний контентный репозиторий.
