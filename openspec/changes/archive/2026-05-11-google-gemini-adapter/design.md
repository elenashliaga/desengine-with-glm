## Context

Система уже движется к модели “один общий LLM-слой + несколько отдельных адаптеров”. Google Gemini должен добавляться именно как отдельный адаптер, а не как разрастание существующих интеграций OpenAI или Ollama.

## Goals / Non-Goals

**Goals:**
- Добавить отдельный адаптер для Google Gemini.
- Зафиксировать минимальную конфигурацию и способ авторизации.
- Подключить `start` и `iterate` к этому адаптеру через единый LLM-слой.

**Non-Goals:**
- Одновременная реализация других провайдеров в этом change.
- Унификация всех провайдеров до полного общего формата без provider-specific логики.
- Автоматический импорт всех моделей провайдера без явного решения.

## Decisions

- Google Gemini добавляется как отдельный адаптер в существующую модель провайдеров.
- Авторизация выполняется по Gemini API key.
- Endpoint и формат запросов следуют Gemini API.
- Минимальная конфигурация включает API key, model и при необходимости базовый URL.
- Если Gemini возвращает provider-specific сведения о safety или blocked responses, адаптер должен переводить их в понятные сообщения пользователя.

## Risks / Trade-offs

- [Provider-specific API] → адаптер неизбежно содержит знание о формате конкретного провайдера → это допустимо, потому что каждый провайдер идёт отдельным change.
- [Несовпадение метрик] → токены, стоимость и диагностические поля могут отличаться от OpenAI → общий LLM-слой должен уметь хранить “метрики есть / метрик нет”.
- [Изменения API провайдера] → provider-specific интеграция может требовать доработок → изоляция в отдельном адаптере уменьшает область изменений.
- [Лимит inline-изображений] → Gemini inline-изображения удобны для MVP, но общий размер запроса ограничен → если реальные задания начнут упираться в лимит, follow-up должен перевести Gemini-адаптер на Files API для крупных изображений или повторного использования файлов.
