## Why

Сейчас OpenSpec фиксирует требования и сценарии поведения, но тестовый контур не оформлен как отдельный, понятный человеку слой:

- часть unit-тестов уже есть, но нет единой команды и инструкции, которые отвечают на вопрос «что прогнать перед правкой / перед закрытием change»;
- нет формальной связи `openspec/specs/**` с тестами, поэтому спецификация может расходиться с реальным поведением незаметно;
- новые changes можно вести без ясной тестовой части и без понимания, какие проверки должны попасть в общий слой;
- credentials, mock-режимы и фикстуры не описаны как воспроизводимый механизм;
- браузерные и пользовательские сценарии не выделены отдельно от unit-проверок.

Нужен слой тестирования, который человек может запускать и развивать небольшими шагами: быстрый для повседневной разработки, полный для проверки change, трассируемый к OpenSpec и не блокирующий основной runtime во время своего постепенного развития.

## What Changes

- Вводим capability `testing-layer`: единый тестовый слой, связанный с OpenSpec, но реализуемый поверх уже установленного стека Vitest/Storybook/Playwright без изменения install-critical инфраструктуры.
- Делим проверки на уровни:
  - **static/contract**: проверка OpenSpec, документации и traceability-метаданных;
  - **unit**: быстрые Node-тесты чистой и серверной доменной логики;
  - **component/browser**: Storybook/Vitest browser для UI-компонентов и визуально-интерактивных состояний;
  - **integration**: проверки API/server-flow на детерминированных данных и mock-провайдерах;
  - **e2e smoke**: короткие браузерные сценарии критического пользовательского пути;
  - **provider/live**: опциональные проверки с реальными credentials, исключённые из обычного обязательного прогона.
- Вводим traceability `test ↔ spec`:
  - каждый тестовый набор, претендующий на покрытие OpenSpec, явно указывает capability и сценарии;
  - отдельная проверка валидирует, что существующие specs имеют связанный минимальный набор тестов;
  - минимальная планка покрытия определяется по requirement/scenario, а не по процентам строк.
- Вводим команды запуска:
  - быстрый smoke для повседневной проверки;
  - полный локальный прогон тестового слоя;
  - выборочный запуск по capability/spec;
  - отдельный live/provider-прогон, который требует credentials и не запускается случайно.
- Описываем работу с credentials и mock-данными:
  - секреты не хранятся в git;
  - обычные тесты используют mock/fixture-данные;
  - live-проверки явно пропускаются или падают с понятной диагностикой, если нет нужных переменных окружения.
- Обновляем правила OpenSpec/change-процесса:
  - каждый новый change должен включать тестовую часть: какие сценарии он добавляет/меняет, какой уровень проверки нужен, какая команда подтверждает результат;
  - тестовый слой можно расширять постепенно, не превращая каждую продуктовую правку в крупный рефакторинг тестов.

## Capabilities

### New Capabilities

- `testing-layer`: единый слой тестирования, команды запуска, traceability к OpenSpec, правила fixture/mock/live-проверок.

### Modified Capabilities

- `admin-tools`: команды и документация сопровождения получают отдельные тестовые команды.
- `openspec`: правила разработки уточняются через новый capability: каждый change обязан описывать интеграцию своей проверки в общий тестовый слой.

## Impact

- Тестовая инфраструктура:
  - добавляются каталоги для spec-oriented тестов, fixtures/helpers и e2e/integration-проверок;
  - добавляются npm scripts поверх существующих инструментов;
  - добавляется проверка traceability.
- Документация:
  - `docs/testing-layer.md` становится человеческой инструкцией по запуску и добавлению тестов;
  - change-шаблоны или guidance получают тестовый чеклист.
- OpenSpec:
  - change получает delta-spec `testing-layer`, чтобы `openspec validate testing-layer --strict` был закрываемым;
  - после реализации capability будет заархивирован в `openspec/specs/testing-layer/spec.md`.
- Credentials:
  - для внешних LLM/provider-сценариев нужен отдельный live-контур через env;
  - обязательный smoke/full не должен требовать реальных ключей.

## Phasing

Реализация должна идти поэтапно:

1. Сначала зафиксировать контракт, документацию и команды, которые ничего не ломают в runtime.
2. Затем добавить traceability-проверку в мягком режиме и покрыть уже существующие unit-тесты метаданными.
3. Потом расширять покрытие по приоритетным specs: access-control, llm, task/task-levels, user-progress, onboarding.
4. После этого добавить короткие e2e smoke-сценарии и integration-проверки API/server-flow.
5. Только после стабилизации включать строгие проверки покрытия specs в обязательный full-прогон.

Обычная разработка основной кодовой базы не должна зависеть от завершённости этого change: незавершённые части тестового слоя запускаются отдельными командами и не меняют поведение `npm run dev`, runtime или продуктовых экранов.
