## Контекст

В кодовой базе уже есть серверная модель статусов `getSystemStatusModel()` и отдельный экран допуска `/auth`, который использует эту диагностику. Конфликт сосредоточен в двух местах:

- `app/page.tsx` всё ещё делает redirect на `/tasks`;
- `app/tasks/page.tsx` не требует allowlist-допуск, хотя вложенные маршруты задач и уровней уже защищены.

## Решение

1. Корневой маршрут `/` становится отдельной публичной страницей состояния.
   - Страница читает `getSystemStatusModel()`.
   - Страница показывает только диагностику, пояснение про защищённые разделы и ссылки на публичные entry point'ы.
   - Страница не рендерит список задач и не требует полной конфигурации или allowlist для самого открытия.

2. Индекс задач `/tasks` приводится к тому же access-контракту, что и остальные защищённые страницы.
   - Перед рендером вызывается `requireAccessOrRedirect(getTasksRootUrl())`.
   - Пользователь без допуска уходит на `/auth` через уже существующий механизм сохранения возвратного path.

3. Спеки синхронизируются вокруг нового root-контракта.
   - `navigation` фиксирует `/` как публичную статусную страницу.
   - `access-control` явно отделяет публичный корень от защищённых разделов.
   - Обзорная спека и внешний локальный онбординг используют одинаковое описание первого входа.

## Проверка

- `npm run lint`
- `npm run build`
- браузерная проверка на `http://localhost:<port>`:
  - `/` открывается без допуска и без redirect;
  - `/tasks` без допуска переводит на `/auth`;
  - `/auth` и `/config` остаются доступны как публичные страницы.
