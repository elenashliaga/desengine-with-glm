## Context

На текущий момент в репозитории сложился двухуровневый layout:
- в корне находятся общие документы, `openspec`, root-скрипты, `packages/`, `utils/` и часть служебных файлов;
- в `lab/` находится фактическое веб-приложение со своим `package.json`, lockfile, Next-конфигом, app router, assets, задачами и runtime-логикой.

Исторически это могло быть удобно как временная изоляция лаборатории, но сейчас структура уже противоречит фактическому продукту:
- пользовательский и админский сценарии описываются как сценарии одного продукта;
- команды установки и запуска всё равно стартуют от корня;
- локальный конфиг и основные сценарии уже документируются как часть общего `desengine`;
- почти любое изменение вынуждено одновременно учитывать и корень, и `lab/`.

Пользователь явно зафиксировал целевую модель:
- итоговый продукт живёт в корне репозитория;
- каталог `lab/` исчезает;
- текущий корень не должен быть уничтожен при переносе;
- при конфликтах технические файлы берутся из `lab/`, а описательные файлы сливаются вручную.

## Goals / Non-Goals

**Goals:**
- Свести repo к одной канонической структуре приложения в корне.
- Поднять всё нужное из `lab/` на верхний уровень без потери важного текущего содержимого корня.
- Сохранить текущее install-critical поведение продукта при новой файловой структуре.
- Убрать path coupling на `lab/` из кода, документации, OpenSpec и tooling.
- Сделать удаление `lab/` финальным шагом после подтверждённого переноса.

**Non-Goals:**
- Смена технического стека.
- Замена версий `Node.js`, сборщика, `Turbopack` или другой install-critical инфраструктуры.
- Параллельная переработка пользовательского UX, уровней, LLM-потока или allowlist-модели.
- Автоматическое “глухое” копирование `lab/` поверх корня без анализа конфликтов.

## Decisions

- Канонический app root переносится в корень репозитория.
  - После миграции Next-приложение, runtime-конфиги, assets, задачи и related tooling живут в `/`.
  - Каталог `lab/` перестаёт быть отдельным продуктовым корнем.

- Базой слияния остаётся текущий корень репозитория.
  - Мы не заменяем корень слепком `lab/`.
  - Любой перенос должен учитывать, что в корне уже есть значимые файлы и каталоги, которые нельзя потерять молча.

- Для технических файлов действует приоритет версии из `lab/`.
  - Это касается как минимум `package.json`, lockfile, `tsconfig`, Next/Vitest/ESLint/PostCSS-конфигов, app bootstrap и похожих инфраструктурных файлов.
  - Если в корне есть уникальная техническая логика, она должна быть вмержена в итоговую корневую версию, но отправной точкой считается файл из `lab/`.

- Для описательных и narrative-файлов действует ручной merge.
  - `README`, onboarding-тексты, platform notes, вспомогательные markdown-файлы и похожие документы нельзя бездумно перезаписывать ни версией корня, ни версией из `lab/`.
  - Для них нужен осознанный итоговый текст, который сохраняет важный текущий корневой контекст и новые факты из `lab/`.

- Удаление `lab/` допускается только после завершения миграции.
  - Сначала нужно перенести файлы, перепривязать пути, обновить команды и проверить, что нужное содержимое корня сохранено.
  - Лишь после этого `lab/` можно удалять как опустевший legacy-каталог.

- Все path assumptions на `lab/` должны быть инвентаризированы и устранены.
  - Это включает код, shell-скрипты, smoke-check, документацию, OpenSpec, внутренние диагностические сообщения и абсолютные markdown-ссылки.
  - Миграция считается завершённой только если официальный сценарий установки и запуска больше не требует существования `lab/`.

- Install-critical стек менять нельзя.
  - Миграция layout не является разрешением на смену `Node.js`-требований, сборщика, `Turbopack` и другой критичной инфраструктуры.
  - Реализация должна сохранить существующий технический стек и добиться переезда за счёт структурной миграции, а не за счёт технологической замены.

- Нужно заранее выделить конфликтные классы файлов.
  - Минимум отдельно рассматриваются:
    - runtime/web app directories (`app`, `components`, `public`, `lib`, `tasks`, `levels`, `content`, `generated`, `prompts`, `tools`);
    - technical root files (`package.json`, lockfile, `tsconfig*`, `next.config.*`, `eslint.config.*`, `postcss.config.*`, `components.json`);
    - docs and markdown (`README`, `INSTALL`, `docs/**`, `env/**`, `AGENTS`-related notes where relevant);
    - shared automation/support (`scripts`, `packages`, `utils`, `openspec` references).
  - Для каждого класса нужно явно решить: прямой перенос, merge, rename/update path, или сохранение как есть.

## Risks / Trade-offs

- [Большой файловый перенос] → можно случайно потерять уникальные корневые файлы или перетереть их содержимым `lab/` → нужен явный этап инвентаризации и ручной разбор конфликтов.
- [Переезд tooling в корень] → можно сломать install/run/build из-за скрытых path assumptions → все команды и скрипты нужно перепроверить после перепривязки.
- [Обновление документации и OpenSpec] → можно оставить “хвосты” со ссылками на `lab/` → нужна отдельная задача на path hygiene и текстовую синхронизацию.
- [Сильный structural diff] → ревью и rollback станут сложнее → реализацию лучше делать как одну целостную миграцию, но по внутреннему чек-листу классов файлов.
- [Приоритет технических файлов из `lab/`] → можно случайно выбросить полезные root-level technical hooks → приоритет не означает слепую замену, нужен merge поверх базы корня.

## Pre-Implementation Checklist

- Подтвердить список root-level файлов и каталогов, которые нельзя потерять при миграции:
  - `openspec/`
  - `README.md`
  - `INSTALL.md`
  - `docs/`
  - `scripts/`
  - `packages/`
  - `utils/`
  - `AGENTS.md`

- Составить карту переноса для runtime-содержимого из `lab/`:
  - `app/`
  - `components/`
  - `public/`
  - `lib/`
  - `tasks/`
  - `levels/`
  - `content/`
  - `generated/`
  - `prompts/`
  - `env/`
  - `tools/`
  - `proxy.ts`

- Отдельно выписать технические root-конфликты, где стартовой версией считается файл из `lab/`:
  - `package.json`
  - `package-lock.json`
  - `tsconfig.json`
  - `next-env.d.ts`
  - `next.config.ts`
  - `eslint.config.mjs`
  - `postcss.config.mjs`
  - `components.json`
  - `vitest.config.ts`
  - `vitest.shims.d.ts`
  - `.gitignore`

- Отдельно выписать narrative-конфликты для ручного merge:
  - `README.md`
  - `INSTALL.md`
  - `docs/**`
  - `env/**`
  - `README.md` как источник содержимого для нового корневого текста

- До удаления `lab/` проверить все классы ссылок и привязок к пути:
  - shell-команды и npm-скрипты
  - smoke-check и диагностические сообщения
  - imports и файловые пути в runtime-коде
  - markdown-ссылки на локальные файлы
  - OpenSpec-спеки и change-артефакты

- Перед началом реализации подтвердить стратегию merge для каждого спорного класса:
  - “перенос как есть”
  - “техническая версия из `lab/` + ручное встраивание root-логики”
  - “ручной narrative merge”
  - “сохранить root-файл без замены, только обновить ссылки”
