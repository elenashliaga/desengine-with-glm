## Context

В системе уже есть сильная основа для level-aware работы с файлами:
- у `LevelConfig` есть `editableFileIds`;
- `TaskLabContext` уже пробрасывает их в интерфейс и маршруты;
- path-based task screens уже опираются на допустимые экраны уровня.

Но backend-контракт пока слабее, чем UI-контракт:
- `start` формирует полный список редактируемых файлов из общего `taskWorkbenchFiles`, а не только из разрешённых на уровне;
- `iterate` уже фильтрует пользовательский выбор по `editableFileIds`, но всё равно должен жёстко игнорировать любые запрещённые ключи из ответа LLM;
- файловая система может содержать рабочие файлы, которых на текущем уровне быть не должно.

Пользователь уточнил целевое поведение: запрещённые для уровня файлы не должны блокировать работу. Их нужно автоматически удалять и продолжать сценарий.

## Goals / Non-Goals

**Goals:**
- Превратить `editableFileIds` в жёсткий allowlist записи и хранения рабочих файлов.
- Не позволять `start` и `iterate` создавать или обновлять запрещённые файлы.
- Автоматически удалять с диска запрещённые рабочие файлы текущего уровня.
- Сохранить непрерывность потока: лишние файлы не должны приводить к пользовательской ошибке.

**Non-Goals:**
- Расширение или изменение самого набора `taskWorkbenchFiles`.
- Изменение дидактических правил уровней.
- Введение нового пользовательского UI для управления лишними файлами.
- Очистка базовых артефактов задачи вроде `base.png`, `variants.png` или `config.json`, если они не относятся к рабочим редактируемым файлам.

## Decisions

- `editableFileIds` уровня становятся каноническим allowlist рабочих файлов.
  - На текущем уровне разрешены только те рабочие fileId, которые входят в `editableFileIds`.
  - Это правило распространяется и на UI, и на backend, и на фактическое состояние файлов на диске.

- Результат LLM применяется только в пределах level allowlist.
  - Если в payload от LLM приходит файл, не разрешённый на текущем уровне, backend игнорирует его.
  - Такой файл не создаётся и не обновляется на диске.
  - Это касается и `iterate`, и инициирующего `start`.

- Перед завершением `start` и `iterate` система чистит диск от запрещённых рабочих файлов.
  - Если файл относится к общему рабочему набору `taskWorkbenchFiles`, но не входит в `editableFileIds` текущего уровня, он должен быть удалён из директории задачи.
  - После удаления система продолжает работу, не выбрасывая пользовательскую ошибку.

- Очистка должна быть level-aware, а не абсолютной.
  - Удаляются только рабочие файлы из управляемого набора компонента.
  - Служебные, входные и нерелевантные для этого контракта файлы не должны затрагиваться этой механикой.

- `start` должен использовать allowlist так же строго, как и `iterate`.
  - Нельзя просить LLM стабильно возвращать полный набор файлов, если часть из них запрещена на уровне.
  - Инициирующий запуск нового уровня должен работать только с разрешённым подмножеством файлов текущего уровня.

- Автоматическая очистка нужна и при входе на уровень, и после итерации.
  - Это гарантирует, что переход между уровнями может убирать раньше созданные файлы, которые на новом уровне запрещены.
  - Это же защищает от случайных “лишних” файлов, пришедших из старых запусков или ручных записей.

- Желательно фиксировать факт фильтрации и очистки в диагностике.
  - Реализация может логировать проигнорированные fileId и удалённые файлы.
  - Но пользовательский основной поток не должен ломаться только потому, что backend выполнил такую зачистку.

## Risks / Trade-offs

- [Более строгий start-контракт] → часть существующих prompt/schema ожиданий может оказаться завязана на полный набор файлов → это нужно решить на уровне prompt/schema и записи, а не откатывать allowlist.
- [Автоматическое удаление файлов] → можно потерять “полезные заготовки” из старших уровней при возврате к младшему или при старом состоянии задачи → это допустимо, потому что текущий уровень должен определять единственно допустимый рабочий набор.
- [Разрыв между prompt-history и диском] → в истории могут встречаться `changedFileIds`, относящиеся к уже запрещённым файлам из прошлых запусков → это приемлемо, если новые записи и текущее состояние диска после change уже соответствуют allowlist.
- [Неполный cleanup scope] → если забыть очистить один из путей записи, контракт будет enforce-иться не везде → нужен единый общий механизм allowlist-фильтрации и disk cleanup.

## Pre-Implementation Checklist

- Подтвердить список fileId, входящих в управляемый рабочий набор `taskWorkbenchFiles`.
- Подтвердить, что `editableFileIds` уже корректно нормализуются относительно известных fileId.
- Выделить все точки записи рабочих файлов:
  - инициирующий `start`
  - обычный `iterate`
  - прямые file update routes, если они могут создавать запрещённые файлы
- Зафиксировать, какие именно файлы на диске считаются рабочими и подлежат автоматической зачистке.
- Проверить, что task routes и UI уже умеют не пускать пользователя на запрещённые file screens, чтобы backend- и frontend-контракты совпадали.
