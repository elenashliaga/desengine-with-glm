## Context

По текущему коду уже видно, что интерфейс системы находится в промежуточном состоянии:
- многие части уже используют `next/link`, `next/image` и shadcn/ui-компоненты вроде `Button`, `Input`, `Textarea`, `Tabs`, `AlertDialog`;
- при этом в отдельных местах остаются сырые элементы:
  - raw `<button>` в системных карточках/панелях;
  - raw `<input>` в отдельных внутренних UI-кусках;
  - raw `<select>` в системных селекторах;
  - raw `<a>` в местах, где у нас уже есть навигационный слой и готовые UI-обёртки.

Само по себе наличие HTML-тегов не всегда плохо, но в системной оболочке это создаёт неоднородность именно там, где у нас уже есть готовый и более надёжный слой abstractions:
- `next/link` и `next/image` уже являются каноническими компонентами Next.js для ссылок и изображений в интерфейсе;
- shadcn/ui уже поставляет набор базовых компонентов, которые команда использует в основной части системы;
- при смешении raw и wrapped элементов становится сложнее поддерживать единые стили, поведение и review-правила.

## Goals / Non-Goals

**Goals:**
- Зафиксировать единый принцип использования надёжных framework/UI-компонентов в интерфейсе системы.
- Провести инвентаризацию мест, где ещё остались raw элементы при наличии канонического эквивалента.
- Мигрировать такие места на `next/link`, `next/image` и shadcn/ui-компоненты.
- Ясно отделить интерфейс самой системы от пользовательского содержимого в `/user/**`.

**Non-Goals:**
- Полная замена всех HTML-элементов в репозитории без разбора.
- Переписывание самих shadcn/ui primitives, которые внутри по определению оборачивают native elements.
- Изменение пользовательского содержимого внутри `/user/**` как части этого change.
- Смена технического стека UI.
- Добавление отдельного автоматического lint/check, если для него потребуется новый инфраструктурный контур.

## Decisions

- “Надёжные компоненты” фиксируются как две группы:
  - канонические framework-компоненты экосистемы Next.js/React, когда для задачи есть официальный компонент (`next/link`, `next/image`);
  - UI-компоненты из `components/ui/**`, поставляемые через shadcn/ui слой проекта.

- Change относится только к интерфейсу системы.
  - Под системным интерфейсом понимаются `app/**`, используемые оболочечные компоненты в `components/desengine/**` и другие product-shell части.
  - Пользовательское содержимое в `/user/**` не является scope этого change, потому что это не продуктовая оболочка.
  - `components/ui/**` тоже не являются scope этого change: это слой primitives, на который системный интерфейс должен опираться, а не цель для миграции в рамках этого change.
  - Неиспользуемые legacy-компоненты внутри `components/desengine/**`, которые сейчас не участвуют в маршрутах продукта, могут оставаться вне фактической миграции этого change.

- Raw элемент допустим только если у него нет релевантного канонического эквивалента в текущем стеке.
  - Если эквивалент уже есть, raw элемент в системном UI считается техническим долгом и подлежит замене.
  - Это правило особенно относится к ссылкам, изображениям и базовым form/action controls.

- Нужно отдельно инвентаризировать текущие места расхождения.
  - На момент постановки change уже видны, например:
    - raw `<button>` в `components/desengine/OnboardingUpdateCard.tsx`
    - raw `<input>` в `components/desengine/Propmt/PromptFile/PromptFile.tsx`
    - raw `<select>` в `components/desengine/LabSelect/LabSelect.tsx`
  - При реализации этот список должен быть перепроверен и уточнён.
  - Если компонент из `components/desengine/**` сейчас не используется в маршрутах продукта, реализация может оставить его вне фактической миграции, и это не считается нарушением для текущего change.

- Migration должна уважать существующий shadcn/ui слой.
  - Если у нас уже есть `Button`, `Input`, `Select`, `Textarea` и другие базовые компоненты, системный интерфейс должен использовать именно их.
  - Для ссылок и изображений канонический выбор — `next/link` и `next/image`, если нет специального исключения.

- Change фиксирует review-принцип, а не только разовую миграцию.
  - После его принятия новые системные UI-элементы тоже должны по умолчанию строиться на этих надёжных компонентах.
  - В первой итерации соблюдение правила проверяется через инвентаризацию и review; отдельный автоматический guardrail не обязателен для завершения этого change.

## Risks / Trade-offs

- [Механическая замена raw элементов] → можно случайно изменить поведение или стили конкретного экрана → реализация должна сопровождаться точечной проверкой affected UI.
- [Не все native tags одинаково вредны] → слишком жёсткое правило можно понять как запрет любой HTML-разметки вообще → поэтому контракт ограничен случаями, где уже есть релевантный канонический компонент.
- [shadcn/ui как слой поверх native] → часть компонентов всё равно рендерит обычные теги внутри → это нормально, потому что цель change не убрать HTML, а стандартизовать точки использования на уровне системного интерфейса.

## Pre-Implementation Checklist

- Зафиксировать полный список raw `<a>`, `<button>`, `<input>`, `<select>`, `<textarea>`, `<img>` в системном UI.
- Разделить найденные случаи на:
  - должны быть заменены на `next/link` / `next/image`
  - должны быть заменены на shadcn/ui
  - допустимы как есть, если эквивалента в текущем слое нет
- Отдельно исключить из scope содержимое `/user/**`, чтобы не смешивать продуктовую оболочку и пользовательский контент.
- Отдельно исключить из scope `components/ui/**`, чтобы не смешивать product-shell migration и поддержку самих primitives.
