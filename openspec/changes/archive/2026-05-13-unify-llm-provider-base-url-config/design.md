## Context

У проекта уже есть общий LLM-слой и отдельные адаптеры провайдеров. На уровне пользовательского ожидания это единая подсистема: оператор выбирает `LLM_PROVIDER`, задаёт параметры активного провайдера и получает одинаковое поведение независимо от бренда провайдера.

Сейчас это ожидание нарушается: provider-specific параметры моделей и endpoint'ов названы неоднородно, часть из них использует префикс ``, а OpenAI живёт по отдельному правилу и получает фактический `base URL` из hardcoded fallback в коде. Это делает OpenAI «особенным» без явного контракта и усложняет переносимость, проксирование и локальную диагностику.

## Goals / Non-Goals

**Goals:**

- Зафиксировать единый контракт конфигурации для всех поддерживаемых LLM-провайдеров.
- Убрать префикс `` из provider-specific параметров моделей и endpoint'ов.
- Убрать зависимость реального `base URL` от захардкоженного значения в адаптере.
- Сделать OpenAI, DeepSeek и Gemini одинаково настраиваемыми через env-конфиг.
- Согласовать документацию и проверки конфигурации с новым единым правилом.

**Non-Goals:**

- Не добавлять новых LLM-провайдеров в этом change.
- Не менять формат самих API-запросов к OpenAI, DeepSeek или Gemini сверх конфигурационной унификации.
- Не переделывать систему выбора активного провайдера.

## Decisions

### 1. У всех провайдеров одинаковая конфигурационная форма

Для каждого поддерживаемого LLM-провайдера система SHALL иметь единый набор env-настроек:
- ключ доступа;
- модель;
- `base URL`.

Provider-specific параметры модели и `base URL` SHALL именоваться без префикса ``. Системный переключатель активного провайдера `LLM_PROVIDER` при этом остаётся отдельной общей настройкой верхнего уровня.

Альтернатива: оставить OpenAI как специальный случай.
Почему не она: это сохраняет административную неконсистентность и нарушает общий контракт LLM-слоя.

### 2. Runtime не должен брать фактический endpoint из скрытого literal в адаптере

Адаптер SHALL работать на основании явной конфигурации и проектных правил, а не на скрытом hardcoded `base URL`, который невозможно увидеть в обычной настройке окружения.

Альтернатива: держать hardcoded default как «удобный fallback».
Почему не она: такой fallback скрывает реальную конфигурацию, мешает прокси/зеркалам и делает поведение OpenAI отличным от остальных провайдеров.

### 3. Provider-specific имена должны быть согласованы и не использовать ``

OpenAI, DeepSeek и Gemini SHALL использовать одну и ту же схему именования provider-specific env-параметров без префикса `` для `model` и `base URL`.

Альтернатива: оставить старые имена с `` только ради обратной совместимости.
Почему не она: это закрепит неоднородность прямо в контракте. Если понадобится миграционный мост на реализации, он должен быть временным и явно задокументирован, а не считаться целевой формой.

## Risks / Trade-offs

- [Риск] Переименование provider-specific env-переменных потребует аккуратной миграции локальных конфигов. → Митигация: зафиксировать явный шаг обновления документации и, при необходимости на реализации, временную диагностику или совместимость.
- [Риск] Полный отказ от hardcoded default может ухудшить DX, если `base URL` забыли задать. → Митигация: требовать понятную ошибку конфигурации вместо неявного поведения.
- [Риск] Часть тестов и статусных подсказок может остаться привязанной к старому имени переменной. → Митигация: включить согласование документации и проверок в обязательные задачи change.

## Migration Plan

На уровне контракта change вводит целевую унифицированную схему. Реализация должна обновить шаблон конфига, провайдерские документы и диагностику так, чтобы оператор явно видел новые ожидаемые имена provider-specific переменных без `` и отсутствие скрытого `base URL` в коде.

Если на этапе реализации понадобится временный миграционный мост со старых имён переменных, он должен считаться переходным механизмом, а не частью целевого контракта.
