## Context

Сейчас проект использует два разных механизма конфигурации:
- структурный `desengine.config.json` для общей конфигурации приложения;
- автоматическую загрузку переменных окружения Next.js через `.env.local` для секретов и локальных runtime-настроек.

Для локального онбординга это оказалось неудобно: ключевые шаги зависят от скрытого файла без расширения, а документация вынуждена каждый раз объяснять не только что в нём заполнить, но и как вообще его создать и отредактировать. Пользовательский запрос на `desengine.config.txt` означает не смену формата значений, а смену носителя и точки входа.

## Goals / Non-Goals

**Goals:**
- Сделать локальный конфиг редактируемым как обычный текстовый файл.
- Сохранить текущий набор переменных и их семантику без изменения контрактов `OPENAI_API_KEY`, `DESENGINE_OPENAI_MODEL`, `DESENGINE_ALLOWLIST_BASE_URL`, `DESENGINE_ALLOWLIST_SALT`.
- Сохранить один общий локальный конфиг-файл для LLM и allowlist-настроек.
- Оставить типовые значения модели, allowlist URL и salt в шаблоне, чтобы человек менял только то, что действительно должно отличаться между установками.
- Дать в шаблоне короткие встроенные подсказки по переименованию файла и по источнику OpenAI API key.
- Синхронизировать документацию и диагностические подсказки с новым именем файлов.

**Non-Goals:**
- Переход на новый формат вроде JSON, TOML или YAML.
- Пересмотр набора локальных переменных лаборатории.
- Изменение значения дефолтной модели, базового allowlist URL или salt-шаблона в рамках этого change.
- Полный редизайн страницы статусов или онбординг-потока.

## Decisions

- Канонический локальный конфиг переносится в `desengine.config.txt`.
  - Файл остаётся локальным и не должен попадать в репозиторий.
  - Формат строк сохраняется env-подобным: `KEY=VALUE`, `#`-комментарии, по одной паре на строку.

- Версионируемый шаблон называется `desengine.config-example.txt`.
  - Первая строка шаблона прямо говорит, что файл нужно переименовать в `desengine.config.txt`.
  - Это снимает двусмысленность между “скопировать” и “создать рядом ещё один файл”.

- В шаблоне очищается только `OPENAI_API_KEY`.
  - `DESENGINE_OPENAI_MODEL`, `DESENGINE_ALLOWLIST_BASE_URL` и `DESENGINE_ALLOWLIST_SALT` остаются заполненными типовыми значениями.
  - Таким образом, пользователь не восстанавливает руками значения, которые являются частью рекомендуемой стартовой конфигурации лаборатории.

- Подсказка про ключ должна быть встроена прямо в шаблон.
  - Короткий комментарий возле `OPENAI_API_KEY` должен вести человека в OpenAI Platform, в раздел API keys.
  - Опираемся на официальную формулировку из OpenAI docs: ключ создаётся через профиль в OpenAI Platform и экран `View API keys`.

- Загрузка `desengine.config.txt` становится явной частью bootstrap-логики.
  - Next.js автоматически подхватывает `.env.local`, но не будет автоматически читать произвольный `desengine.config.txt`.
  - Поэтому проекту нужен один явный способ прочитать `desengine.config.txt` и положить значения в `process.env` до первого использования LLM и allowlist-конфигурации.
  - Ту же логику должен использовать smoke-check, чтобы диагностика и рантайм не расходились.

- Приоритет прямых переменных окружения сохраняется.
  - Если переменная уже задана в окружении процесса, она должна переопределять значение из `desengine.config.txt`.
  - Это сохраняет совместимость с CI, одноразовыми shell-запусками и будущими override-сценариями.

- Документация и интерфейсные подсказки считаются частью изменения.
  - Все упоминания `.env.local` и `.env.local.example` в пользовательской и админской документации нужно заменить на новый путь и новый шаблон.
  - Сообщения в интерфейсе, smoke-check и вспомогательных скриптах должны подсказывать именно `desengine.config.txt`.

## Risks / Trade-offs

- [Уходим с автозагрузки Next env] → можно случайно получить расхождение между dev/build/start и вспомогательными скриптами → нужен единый загрузчик `desengine.config.txt`, переиспользуемый во всех точках входа.
- [Сохраняем env-подобный формат в `.txt`] → человек может ожидать произвольный текст, хотя синтаксис остаётся строгим → это компенсируется простым шаблоном и короткими комментариями в файле.
- [Предзаполненный salt в примере] → кто-то может оставить шаблонное значение без замены → документация и статусные проверки должны явно объяснять, когда это допустимо для локального знакомства, а когда нужен рабочий секрет.
- [Новый файл отличается от привычных `.env` практик] → разработчик может по инерции продолжить редактировать старый `.env.local` → нужно удалить двусмысленность в документации и диагностике, а не поддерживать два равноправных пути.
