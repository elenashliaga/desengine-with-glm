## Context

В текущем репозитории уже есть несколько утилит, которые по смыслу относятся именно к админскому контуру:
- `scripts/smoke-local-install.mjs` — smoke-check локальной установки;
- `tools/generate-allowlist-marker.mjs` — генерация allowlist-маркера;
- `utils/config.sh` — служебная генерация task config;
- `utils/generate_task_folders.sh` — служебная подготовка task-каталогов.

Их текущее состояние неоднородно:
- часть уже на JS и запускается через npm;
- часть всё ещё на bash;
- shell-скрипты используют жёсткие абсолютные пути и утилиты окружения вроде `magick`;
- инструкции по использованию этих инструментов рассеяны по общим документам.

Если оставить всё как есть, админский контур будет всё сильнее расползаться: новые утилиты будут появляться то в `scripts/`, то в `tools/`, то в `utils/`, а запуск и документация останутся несобранными.

## Goals / Non-Goals

**Goals:**
- Собрать админский инструментарий в одном каталоге `/tools`.
- Зафиксировать полный текущий список админских утилит как часть change.
- Сделать `npm run ...` каноническим способом запуска админских инструментов.
- Убрать зависимость официального админского контура от bash-скриптов как entry point.
- Собрать инструкции по этим инструментам в Markdown внутри `/tools`.

**Non-Goals:**
- Перенос пользовательского runtime-кода в `/tools`.
- Полная ликвидация любых внутренних shell-фрагментов во всём репозитории независимо от назначения.
- Изменение install-critical стека проекта.
- Перепридумывание самих бизнес-операций админских утилит сверх их организационного переноса.

## Decisions

- `/tools` становится единым домом для админских утилит.
  - Канонические админские скрипты и связанные с ними markdown-инструкции должны жить только в `/tools`.
  - Каталоги `scripts/` и `utils/` не должны оставаться альтернативными официальными точками входа для админских действий.

- Инвентаризация текущих админских утилит обязательна и входит в scope change.
  - На момент постановки change к таким утилитам как минимум относятся:
    - `scripts/smoke-local-install.mjs`
    - `tools/generate-allowlist-marker.mjs`
    - `utils/config.sh`
    - `utils/generate_task_folders.sh`
  - При реализации список должен быть перепроверен и, если нужно, расширен на другие admin-only утилиты.

- Канонический способ запуска админских утилит — через npm scripts.
  - Пользователь или оператор не должен помнить прямые пути к скриптам как официальный способ работы.
  - Entry point должен выглядеть как `npm run <admin-command>`.

- Bash-скрипты админского контура переводятся на JS.
  - Shell-варианты не считаются официальным способом сопровождения после этого change.
  - Реализация должна заменить их JS-утилитами, совместимыми с npm-driven запуском.

- Markdown-инструкция по админским утилитам живёт в `/tools`.
  - Допустим один общий файл с перечнем команд и назначений.
  - Допустимы и несколько тематических markdown-файлов, если все они находятся в `/tools`.
  - Главное — не держать каноническую инструкцию по admin tools вне этого каталога.

- Change не меняет технический стек продукта.
  - Перевод bash-утилит на JS не должен вести к смене install-critical инфраструктуры.
  - Нужно использовать уже допустимый для проекта Node/npm-контур.

- Нужно убрать жёсткую привязку к локальным путям из официального админского контура.
  - Скрипты, завязанные на абсолютные пути конкретной машины, не подходят как канонические admin tools.
  - После миграции официальный инструмент должен опираться на repo-relative конфигурацию, явные аргументы или документированные параметры.

## Risks / Trade-offs

- [Перевод shell в JS] → можно случайно потерять часть текущего поведения служебных скриптов → нужна инвентаризация фактических сценариев использования до переписывания.
- [Сборка инструкций в `/tools`] → информация частично будет дублироваться с `README`/`INSTALL`/`env/*.md` → это допустимо, если `/tools` становится канонической точкой именно для admin tools, а общие документы только ссылаются на неё.
- [npm как единственный entry point] → придётся придумать понятные имена команд и поддерживать их стабильными → это нормальная цена за единый интерфейс админского контура.
- [Админские скрипты с жёсткими путями] → часть текущих локальных полуразовых утилит может оказаться слишком machine-specific для официального контура → это допустимо, потому что change как раз должен отделить канонические admin tools от случайных локальных helper-скриптов.

## Pre-Implementation Checklist

- Подтвердить полный список скриптов, которые считаются admin-only.
- Разделить их на:
  - уже JS и npm-friendly
  - shell-only
  - machine-specific и требующие нормализации
- Зафиксировать целевую структуру `/tools`:
  - сами исполняемые JS-утилиты
  - markdown-инструкция
  - при необходимости вспомогательные шаблоны/ресурсы, если они относятся к admin tools
- Подготовить карту соответствия “старый путь → новый путь → новый npm command”.
