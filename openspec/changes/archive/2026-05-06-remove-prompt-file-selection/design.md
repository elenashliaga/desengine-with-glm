## Context

Текущий контракт уточняющего промпта исторически строился вокруг идеи “пользователь сам выбирает вводные файлы”. Это видно в нескольких слоях:
- `openspec/specs/iteration/spec.md` описывает выбранные пользователем вводные файлы;
- `openspec/specs/component-file-set/spec.md` отдельно фиксирует выбор подмножества input files;
- `components/desengine/Propmt/Prompt.tsx` и `PromptFileList` показывают UI выбора файлов;
- `app/api/tasks/[taskId]/iterate/route.ts` принимает `selectedFileIds`.

При этом фактическая модель продукта уже сдвинулась:
- у каждого уровня есть `editableFileIds`, то есть список файлов, которые вообще допустимы на текущем уровне;
- backend уже умеет трактовать отсутствие пользовательского списка как “взять все разрешённые”;
- сам уровень уже определяет scope работы пользователя намного сильнее, чем ручные чекбоксы в форме уточнения.

В такой модели выбор файлов перестаёт быть полезной пользовательской свободой и превращается в лишнее решение в интерфейсе.

## Goals / Non-Goals

**Goals:**
- Упростить пользовательский поток уточнения до одного текстового поля.
- Зафиксировать, что в `iterate` всегда участвуют все файлы, разрешённые на текущем уровне.
- Убрать `selectedFileIds` из официального пользовательского и API-контракта.
- Сохранить level allowlist как единственную границу того, какие файлы попадают в контекст и могут быть изменены.

**Non-Goals:**
- Изменение логики allowlist по уровню.
- Изменение структуры самих рабочих файлов.
- Изменение инициирующего `start` beyond already existing “all allowed files” behavior.
- Усложнение UI новыми настройками промпта вместо старых.

## Decisions

- Пользователь больше не выбирает вводные файлы для `iterate`.
  - Уточняющий промпт всегда использует все рабочие файлы, разрешённые `editableFileIds` текущего уровня.
  - Это правило становится обязательной частью контракта, а не просто backend fallback.

- UI уточняющего промпта упрощается до текстового поля и запуска.
  - Список чекбоксов/переключателей файлов уходит из product-shell интерфейса.
  - Пользовательский интерфейс уточнения не должен требовать отдельного решения о составе файлового контекста.

- `selectedFileIds` перестаёт быть обязательной частью `iterate` API-контракта.
  - Официальный путь работы не должен передавать выбор подмножества файлов с клиента.
  - Backend сам строит файловый контекст из level allowlist.

- Level allowlist остаётся единственным механизмом ограничения файлового контекста.
  - Если файл разрешён на уровне, он входит в контекст `iterate`.
  - Если файл запрещён на уровне, он не попадает в контекст и не может быть изменён.

- История уточнений больше не должна описывать пользовательский выбор файлов как отдельное действие.
  - Система может при необходимости хранить фактический набор файлов уровня как вычислимый контекст.
  - Но пользовательский контракт больше не включает действие “я выбрал вот эти файлы”.

## Risks / Trade-offs

- [Убираем пользовательский контроль над подмножеством файлов] → опытные пользователи теряют возможность вручную сужать контекст → это осознанный обмен на простоту и предсказуемость потока.
- [История уточнений меняет смысл] → старые записи могут содержать `selectedFileIds`, а новые уже нет или будут трактоваться иначе → это допустимо, если новый контракт становится единым для всех последующих итераций.
- [Более широкий контекст по умолчанию] → некоторые уточнения будут отправляться с большим количеством файлов, чем раньше → это допустимо, потому что уровень уже ограничивает scope, а продуктовый UX становится проще.

## Pre-Implementation Checklist

- Зафиксировать все места, где `selectedFileIds` участвует в UI, API, истории и спеках.
- Проверить, что backend уже умеет стабильно собирать контекст из всех `editableFileIds` текущего уровня.
- Подготовить решение для backward compatibility истории уточнений, если в старых записях ещё есть `selectedFileIds`.
