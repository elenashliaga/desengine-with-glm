## Context

Сейчас продукт развивается как local-first лаборатория, но его текущее состояние всё ещё ориентировано на внутреннюю разработку. Внешний пользователь, который просто клонирует репозиторий, сталкивается сразу с несколькими типами трения:
- неочевидно, из какого каталога запускать проект;
- неочевидно, какие env действительно обязательны;
- при неполной конфигурации приложение не даёт понятного браузерного статуса системы;
- allowlist-гейт смешан с первым знакомством и не отделён от пользовательской оболочки;
- production build может падать из-за legacy-кода или внешних сетевых зависимостей;
- нет одной команды, которая проверяет “всё ли у меня готово”;
- не зафиксировано, как должен выглядеть одинаковый пользовательский поток на `macOS`, `Windows` и `Linux`.

Если мы хотим просить внешних людей разворачивать репозиторий у себя, продукт должен сначала стать не просто “работающим у нас”, а воспроизводимо поднимаемым у нового человека по инструкции.

## Goals / Non-Goals

**Goals:**
- Зафиксировать минимальный стандарт “репозиторий готов к внешнему локальному развёртыванию”.
- Убрать известные build-blockers и сетевую хрупкость сборки.
- Сделать запуск и первичную проверку установки однозначными.
- Снизить трение первого входа в продукт через общую страницу состояния системы.
- Разделить пользовательский браузерный поток и админские операции настройки.
- Синхронизировать документацию с реальным состоянием приложения.
- Зафиксировать одинаковый по смыслу браузерный UX на `macOS`, `Windows` и `Linux`.

**Non-Goals:**
- Полноценный инсталлятор desktop-приложения.
- Публикация npm-пакетов или контейнерных образов.
- Автоматическое развёртывание в облако.
- Полный CI/CD maturity для всех вспомогательных сценариев.

## Decisions

- Репозиторий должен иметь один официальный сценарий запуска.
  - Внешний пользователь не должен догадываться, запускать ли root или `lab` отдельно.
  - Канонический путь запуска должен начинаться с корня репозитория.

- Production build считается обязательным критерием готовности.
  - Нельзя просить внешних пользователей разворачивать repo, если `next build` нестабилен или зависит от legacy-маршрутов, которые уже не являются официальным потоком.
  - Internal/dev-only сценарии не должны ломать production build внешнего пользовательского контура.

- Сборка не должна зависеть от внешней доступности Google Fonts.
  - Для внешнего локального развёртывания нужны локальные шрифты или надёжный fallback без сетевого fetch на build-time.

- Внешний пользователь должен всегда попадать в pre-access shell.
  - Корневой маршрут `/` должен открываться даже при неполной конфигурации.
  - До допуска пользователь видит одну общую страницу состояния системы, а не список задач и не рабочую часть лаборатории.
  - На этой странице должны быть только статусы готовности и инструкции по следующим шагам.

- Allowlist остаётся обязательным gate для рабочей части лаборатории.
  - Даже если LLM-конфигурация уже введена, без allowlist пользователь не должен попадать в защищённый поток.
  - Под “локальным онбордингом” понимается не bypass защиты, а доступность оболочки и диагностики до допуска.
  - Настройка allowlist относится к админскому/операторскому контуру, а не к пользовательскому потоку.

- Пользовательский поток должен быть браузерным и кроссплатформенным.
  - На `macOS`, `Windows` и `Linux` пользователь должен выполнять одинаковые по смыслу действия через браузер.
  - Shell-утилиты, bash-скрипты и технические операции допускаются только как часть админской настройки.

- Репозиторий должен иметь один официальный smoke-check.
  - Он должен проверять хотя бы: env-конфигурацию, базовую готовность LLM-настроек, конфигурацию allowlist, доступность стартовой страницы и готовность официального пользовательского потока.
  - Проверка может оставаться админским инструментом, даже если пользователь о ней не знает.

- Документация считается частью готовности, а не вторичным артефактом.
  - README, шаблон локальной конфигурации, platform notes и маршрутная модель должны описывать ровно тот продукт, который реально запускается.
  - Пользовательские и админские инструкции должны быть отделены друг от друга.

- Legacy/internal потоки должны быть либо изолированы, либо явно выведены из официального контура.
  - Если маршрут нужен только для внутренней разработки, он не должен участвовать в обещании “внешний пользователь поднимает продукт по инструкции”.
  - Устаревшие сценарии не должны ломать корневой маршрут `/`, production build и pre-access shell.

## Risks / Trade-offs

- [Доступная оболочка до допуска] → можно случайно раскрыть больше пользовательского контента, чем планировалось → до allowlist нужно показывать только страницу состояния и инструкции, без задач и без рабочей части лаборатории.
- [Удаление legacy-маршрутов] → можно случайно сломать внутренние dev-сценарии → перед удалением нужно явно различить официальный и устаревший поток.
- [Один сценарий запуска] → часть гибкости для внутренней разработки уйдёт → это допустимо, если для внешнего пользователя появляется одна ясная точка входа.
- [Smoke-check как обязательство] → придётся поддерживать проверку в актуальном состоянии → это нормальная цена за reproducible onboarding.
- [Кроссплатформенность] → одинаковый смысловой поток на трёх ОС потребует аккуратной документации и отказа от bash-специфичных пользовательских шагов → это допустимо, потому что пользовательский путь всё равно должен оставаться браузерным.
