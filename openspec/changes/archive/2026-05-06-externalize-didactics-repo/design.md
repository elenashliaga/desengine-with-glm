## Status

Superseded by `onboarding-repo`.

Этот design сохранён как исторический шаг. Актуальный контракт теперь фиксируется через onboarding-репозиторий, а не через более узкий didactics-repo.

## Context

Сейчас продукт постепенно наращивает два разных слоя:
- технический слой лаборатории и инфраструктуры;
- образовательный слой: задачи, дидактические промпты, объяснения, материалы.

Если держать всё в одном репозитории, дидактика и код начнут мешать друг другу: разные ритмы изменений, разные ответственные, разный жизненный цикл и разный review-фокус. Поэтому дидактический слой нужно вынести в отдельный репозиторий.

## Goals / Non-Goals

**Goals:**
- Зафиксировать дидактический репозиторий как отдельный источник правды.
- Развести ответственность между кодом продукта и образовательным контентом.
- Подготовить основу для отдельного цикла работы над задачами и дидактическими промптами.

**Non-Goals:**
- Немедленная миграция всех текущих файлов.
- Выбор конкретного механизма интеграции (submodule, subtree, checkout, remote sync, package, CDN и т.д.).
- Реализация загрузки внешнего репозитория в продукте.
- Детализация CI/CD для didactics-repo.

## Decisions

- Дидактика выносится в отдельный репозиторий.
  - Это организационное и архитектурное решение, а не просто файловый рефакторинг.

- На первом этапе обязательный минимум didactics-repo:
  - дидактические промпты;
  - задачи.

- Основной репозиторий остаётся хозяином:
  - лаборатории;
  - runtime;
  - auth/access;
  - интеграции с LLM;
  - технических спецификаций и инфраструктуры продукта.

- Didactics-repo становится хозяином:
  - задач;
  - дидактических промптов;
  - уровня-специфичных образовательных материалов;
  - при необходимости редакторских метаданных.

- Конкретный механизм подключения внешнего репозитория пока не фиксируется.
  - Сначала нужно согласовать модель данных и границы.
  - Затем отдельным change выбрать operational strategy.

## Risks / Trade-offs

- [Два источника изменений] → координация между code repo и didactics-repo усложнится → нужны чёткие границы и явные контракты.
- [Слишком раннее отделение] → если модель данных ещё не устоялась, миграция может дестабилизировать структуру → поэтому этот change пока только про архитектурное решение.
- [Неопределённый механизм интеграции] → пока не выбран способ подключения, реализация будет отложена → это допустимо, потому что сейчас важно зафиксировать именно границу владения.
