## Context

Текущая URL-модель смешивает несколько разных ролей:
- `/` сейчас может быть и страницей допуска, и страницей статусов, и входом в список задач;
- `/lab` используется как контейнер нескольких экранов, где тип экрана и его контекст кодируются query-параметрами;
- after-auth redirect использует параметр `next`, что тащит query и в защищённый контур тоже.

Это противоречит желаемой форме продукта:
- top-level URL должны читаться как карта системы;
- пользователь должен понимать адрес по его структуре, а не по набору параметров;
- страница задачи, страница уровня, auth, config и help должны существовать как самостоятельные маршруты;
- публичная URL-схема должна быть устойчивой к перезагрузке и копированию ссылки без вспомогательных `?screen=` и `?next=`.

Пользователь также отдельно уточнил два принципа:
- внутри задачи экраны нужно кодировать как path-сегменты вида `tasks/<taskId>/<screen>`;
- после допуска нужно возвращать пользователя туда, куда он шёл, но без query-параметров.

## Goals / Non-Goals

**Goals:**
- Зафиксировать одну официальную карту пользовательских URL.
- Убрать query-параметры из официальной пользовательской навигации.
- Сохранить deep link и восстановление контекста после reload.
- Сохранить возврат после допуска на целевой экран без `?next=...`.
- Выделить `auth`, `config` и `help` как отдельные top-level маршруты.

**Non-Goals:**
- Полная проработка содержимого главной страницы `/`.
- Полная проработка UX контента для `help/` и `config/` в рамках этого change.
- Смена allowlist-модели или auth-механизма как такового.
- Введение произвольного router-state в query для отладки или служебных режимов пользовательского интерфейса.

## Decisions

- Публичная URL-схема фиксируется на top-level path-маршрутах.
  - `/` сейчас не является рабочим экраном списка задач и явно редиректит на `/tasks`.
  - `/tasks`, `/levels`, `/auth`, `/config`, `/help` становятся каноническими публичными entry points.

- Список задач живёт по `/tasks`.
  - Пользовательский список всех задач больше не должен зависеть от `/` как от временной стартовой страницы.
  - Это позволит позже отдельно прорабатывать корневую главную страницу без смешения с рабочим каталогом задач.

- Экран задачи и внутренние task-экраны становятся path-based.
  - Базовый адрес задачи: `/tasks/<taskId>`.
  - Внутренние task-экраны: `/tasks/<taskId>/<screen>`.
  - Экран `screen` должен кодировать различимые пользовательские состояния задачи без query-параметров.
  - Значение `screen` совпадает с кодом допустимого для этой задачи файла/экрана.
  - Если `screen` не указан, система открывает экран `Component`.
  - Перезагрузка страницы на таком адресе должна возвращать пользователя в тот же контекст.

- Экран перехода между уровнями получает отдельный канонический path.
  - Для перехода к следующему уровню используется `/tasks/<taskId>/next`.
  - Этот адрес является частью официального task-routing контракта, а не временным query-driven состоянием.

- Уровни получают свою path-based иерархию.
  - `/levels` — полный каталог уровней.
  - `/levels/<levelId>` — конкретный уровень.
  - Query-driven переходы между уровнями не считаются официальной пользовательской навигацией.

- Экран допуска отделяется в `/auth`.
  - Если пользователь ещё не прошёл allowlist, система ведёт его на `/auth`.
  - `/auth` отвечает только за допуск, а не за список задач или рабочий каталог.

- Возврат после допуска хранится без query-параметров.
  - Система должна помнить целевой path пользователя без `?next=...`.
  - Для этого допустим server-managed state: cookie, session или иной краткоживущий механизм, который не превращает адрес страницы в transport для redirect intent.
  - После успешного допуска пользователь возвращается на целевой path, если он валиден и разрешён.

- `/config` и `/help` фиксируются как отдельные top-level страницы.
  - `config` сейчас показывает статусы ключей и другие настройки/диагностику.
  - `help` резервируется под отдельный пользовательский help-контур.
  - Полный контент этих страниц может дорабатываться отдельными change, но сами URL и их роль фиксируются уже сейчас.

- Официальная пользовательская навигация не использует query-параметры.
  - Требование распространяется на человекоориентированные адреса, которыми пользователь пользуется, делится и которые может перезагружать.
  - Внутренние технические API-запросы не считаются пользовательскими URL в этом контракте.
  - Legacy-маршруты вроде `/lab?screen=...` должны быть выведены из официального контура.

## Risks / Trade-offs

- [Переход с `/` на `/tasks`] → корневой маршрут временно становится только redirect point → это допустимо, потому что отдельная проработка главной страницы запланирована позже.
- [Path-based task screens] → придётся явно назвать и стабилизировать набор экранов задачи → это нормальная цена за читаемую и reload-stable URL-схему.
- [Return path без query] → потребуется server-managed state для auth-flow → это усложняет реализацию по сравнению с `?next=`, но делает публичные URL чище и безопаснее.
- [Legacy `/lab` уходит из официального контура] → понадобится миграция ссылок, кнопок и внутренних переходов → это нужно включить в отдельный этап routing cleanup.
