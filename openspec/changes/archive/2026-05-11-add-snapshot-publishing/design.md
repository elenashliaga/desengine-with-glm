## Context

Сейчас задача уже хранит рабочие файлы и историю промптов локально, но эти данные доступны только внутри защищённого интерфейса. Для MVP нужен отдельный publish-flow, который собирает безопасный публичный слепок, сохраняет его как отдельную сущность и отдаёт по стабильному публичному маршруту без требования access-cookie.

## Goals / Non-Goals

**Goals:**
- Дать пользователю явное действие публикации слепка из рабочего экрана задачи.
- Публиковать итоговые текстовые файлы набора компонента и историю промптов.
- Исключить из слепка runtime-конфиг, progress, LLM-метрики, системные промпты и прочие непубличные данные.
- Блокировать публикацию, если в промптах или итоговых файлах найдены признаки секрета.
- Дать публичную страницу просмотра и отдельный JSON-ресурс слепка.

**Non-Goals:**
- Редактирование или удаление опубликованных слепков.
- Мультипользовательские права доступа и внешнее облачное хранилище.
- Публикация PNG-референсов, системных промптов, progress-метаданных или внутренней LLM-телеметрии.

## Decisions

- Слепок сохраняется как отдельный JSON-файл в `user/snapshots/`.
  - Это сохраняет local-first модель и не требует менять install-critical стек.
  - Публичность достигается отдельным незащищённым маршрутом чтения, а не переносом данных в `public/`.

- Публичный идентификатор слепка генерируется отдельно от `taskId`.
  - Пользователь получает стабильную ссылку вида `/snapshots/<snapshotId>`.
  - По этому же `snapshotId` доступен JSON-ресурс слепка.

- В состав слепка входят только текстовые рабочие файлы из фиксированного набора компонента.
  - Берём только `taskWorkbenchFiles` с `edit: true`.
  - Бинарные файлы и любые project-owned или env-owned данные в слепок не попадают.

- История промптов в слепке хранится в пользовательском виде.
  - Включаем текст промпта и полезные пользовательские метаданные (`createdAt`, `displayCreatedAt`, `iterationNumber`, `levelNumber`, изменённые/отправленные файлы).
  - Не включаем `llmCall`, токеновую телеметрию и другие внутренние поля, не нужные для публичного слепка.

- Публикация блокируется при признаках секрета.
  - Перед записью слепка сервер прогоняет содержимое файлов и промптов через набор эвристик.
  - При совпадении возвращаем человеку понятную ошибку без эха найденного секрета.
  - Это безопаснее, чем пытаться автоматически маскировать потенциально критичные данные в уже публикуемом артефакте.

- Публиковать слепок можно только для уже начатой задачи.
  - Это исключает пустые публикации без рабочего состояния.

## Risks / Trade-offs

- [Ложноположительные срабатывания] → простые эвристики могут заблокировать безопасный текст → в ответе нужна понятная причина и указание, где искать проблему.
- [Пропуск редкого секрета] → регулярные выражения не покрывают все форматы → MVP опирается на блокировку самых типовых секретов и строгий whitelist данных слепка.
- [Рост локального хранилища] → публикации будут копировать текущее состояние файлов и истории → на MVP это допустимо, потому что объёмы локальные и контролируемые.
