## Context

Сейчас приложение использует проектные каталоги и файлы сразу для двух ролей:
- как источник канонических task/level-настроек;
- как хранилище живого пользовательского состояния.

По текущим путям это выражено так:
- `tasks/` используется и как каталог описаний задач, и как место, куда пишутся рабочие `Component.tsx`, `styles.ts`, `mock.ts`, `props.ts`, `Component.stories.ts`, `prompt-history.json` и другие runtime-результаты;
- `env/user-progress.json` хранит реальный прогресс пользователя рядом с проектной конфигурацией;
- reset и чтение task state опираются на то, что пользовательские данные лежат прямо в проектном дереве.

Это неудобно для сопровождения и поставки проекта:
- пользовательские данные не отделены от контента, пришедшего из GitHub;
- update проекта и cleanup пользовательских результатов логически смешаны;
- нельзя просто удалить “всё, что сделал пользователь”, не затрагивая проектные исходники.

Пользовательский запрос формулирует ясную целевую модель:
- всё runtime-состояние пользователя живёт в `/user`;
- project data остаётся в versioned части репозитория;
- обычное обновление проекта не должно затрагивать `/user`;
- отсутствие `/user` должно трактоваться как “результатов ещё нет”, а не как ошибка системы.

## Goals / Non-Goals

**Goals:**
- Отделить project data задач и уровней от реального пользовательского состояния.
- Перенести весь live progress и все пользовательские рабочие файлы в `/user`.
- Сделать `/user` безопасным для локального долгоживущего использования между обновлениями проекта.
- Сделать полное удаление `/user` эквивалентом полного сброса пользовательской работы.

**Non-Goals:**
- Изменение дидактической модели уровней или задач.
- Смена технического стека или механики локальной установки.
- Облачная синхронизация пользовательских данных.
- Переезд project data задач и уровней вне репозитория.

## Decisions

- Project data и user state разводятся по разным корням.
  - Project data продолжает жить в versioned каталогах репозитория.
  - User state переезжает в отдельный каталог `/user`.

- В `/user` хранится весь реальный runtime-след пользователя.
  - Это включает:
    - общий прогресс пользователя;
    - рабочие файлы задач, созданные и изменённые по ходу решения;
    - prompt-history и аналогичные runtime-артефакты;
    - другие производные пользовательские результаты, если они не являются канонической частью project data.

- Настройки задач и уровней остаются project data.
  - `levels/` продолжает хранить конфигурацию уровней.
  - Каталоги задач продолжают хранить task metadata, базовые изображения, project-owned конфиги и другие исходные данные задачи.
  - Пользовательская работа не должна больше записываться поверх этих project-owned файлов.

- `/user` должен переживать обновление проекта из GitHub.
  - Каталог `/user` не должен быть частью обычного versioned project payload.
  - Практически это означает, что его нужно исключить из слоя файлов, который обновляется вместе с кодом проекта, и не считать его проектным исходником.

- Отсутствие `/user` является валидным стартовым состоянием.
  - Если каталог отсутствует целиком, система создаёт его по необходимости.
  - Если внутри нет прогресса или рабочих файлов, продукт должен трактовать это как “пользователь начинает с нуля”.

- Полное удаление `/user` эквивалентно полному reset пользовательской работы.
  - После удаления `/user` система не падает.
  - Все задачи считаются не начатыми.
  - Рабочие файлы и history считаются отсутствующими и создаются заново по мере работы пользователя.

- Пути project data и user state должны быть явно различимы в конфигурации.
  - Нельзя оставлять двусмысленность, при которой один и тот же `tasksRoot` одновременно означает и canonical task catalog, и пользовательский workspace.
  - Конфигурация и runtime-хелперы должны уметь различать:
    - где лежит task catalog;
    - где лежит user progress;
    - где лежит user workspace по конкретной задаче.

- Reset и чтение task state должны работать поверх новой модели хранения.
  - Чтение задачи должно собирать итоговое состояние из project data + user state.
  - Сброс задачи должен очищать только user-owned артефакты.
  - Базовые task-конфиги и референсы из project data не должны удаляться при пользовательском reset.
  - Если для совместимости ещё существуют legacy user-owned артефакты в старых project-путях, reset должен очищать и их тоже, чтобы состояние не импортировалось обратно после сброса.

## Risks / Trade-offs

- [Новая карта путей] → можно случайно оставить часть чтения/записи в старых project-каталогах → нужна полная инвентаризация всех runtime write paths.
- [Разделение project data и user state] → чтение задачи станет чуть сложнее, потому что итоговое состояние теперь собирается из двух слоёв → это нормальная цена за чистую модель хранения.
- [Удаление `/user` как reset] → можно скрыть баги инициализации, если система молча не создаёт нужные подкаталоги → нужна явная lazy-init стратегия для user storage.
- [Git hygiene] → если забыть исключить `/user` из project-tracked слоя, обновления могут по-прежнему затрагивать пользовательские файлы → это нужно закрепить и в layout, и в repo hygiene.

## Pre-Implementation Checklist

- Зафиксировать полный список пользовательских runtime-артефактов, которые сейчас пишутся в project tree.
- Разделить текущие пути на:
  - project-owned
  - user-owned
- Выделить все точки чтения и записи:
  - user progress
  - prompt-history
  - рабочие файлы задачи
  - reset/cleanup
  - task start / iterate / manual file updates
- Зафиксировать целевую структуру `/user`, достаточную для:
  - прогресса пользователя
  - рабочего пространства по задачам
  - prompt-history и других runtime-данных
- Проверить, что старт с пустым или отсутствующим `/user` может быть описан как штатный сценарий в OpenSpec.
