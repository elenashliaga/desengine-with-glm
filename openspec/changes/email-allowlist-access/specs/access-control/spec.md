## ADDED Requirements

### Requirement: Доступ в систему проверяется по email до начала работы

Система SHALL требовать ввод email до допуска пользователя к лаборатории и заданиям.

#### Scenario: Пользователь открывает систему
- **WHEN** пользователь впервые открывает систему
- **THEN** система показывает экран проверки доступа по email

### Requirement: Проверка допуска использует удалённый allowlist-маркер

Система SHALL проверять допуск пользователя по существованию удалённого ресурса, адрес которого вычисляется из нормализованного email.

#### Scenario: Пользователь вводит email
- **WHEN** пользователь вводит email и запускает проверку
- **THEN** система нормализует email, вычисляет salted hash и делает запрос к удалённому URL allowlist-маркера

### Requirement: Raw email не публикуется в URL allowlist-маркера

Система SHALL использовать в URL allowlist-маркера salted hash от нормализованного email, а не raw email.

#### Scenario: Формируется URL проверки допуска
- **WHEN** система строит URL allowlist-маркера
- **THEN** в URL не присутствует raw email пользователя

### Requirement: Семантика ответов allowlist-сервера фиксирована

Система SHALL интерпретировать ответы allowlist-сервера следующим образом:
- `200` — доступ разрешён;
- `404` — доступ запрещён;
- любой другой ответ или сетевая ошибка — техническая ошибка проверки.

#### Scenario: Allowlist-маркер найден
- **WHEN** сервер отвечает `200`
- **THEN** система разрешает пользователю работу с лабораторией

#### Scenario: Allowlist-маркер отсутствует
- **WHEN** сервер отвечает `404`
- **THEN** система не допускает пользователя к работе

#### Scenario: Проверка завершилась технической ошибкой
- **WHEN** сервер недоступен или отвечает не `200` и не `404`
- **THEN** система показывает техническую ошибку и не открывает лабораторию

### Requirement: Допуск не сохраняется между открытиями приложения

Система SHALL требовать новую проверку допуска при каждом новом открытии приложения.

#### Scenario: Пользователь заново открывает приложение
- **GIVEN** пользователь ранее уже проходил проверку допуска
- **WHEN** приложение открывается заново
- **THEN** система снова показывает экран проверки доступа по email
- **AND** не считает прошлый успешный допуск достаточным

### Requirement: Без допуска защищены и страницы, и API лаборатории

Система SHALL проверять факт допуска не только в пользовательском интерфейсе, но и на серверной стороне для страниц и API лаборатории.

#### Scenario: Пользователь открывает страницу лаборатории без допуска
- **WHEN** пользователь запрашивает страницу лаборатории без успешной проверки допуска
- **THEN** система не открывает лабораторию

#### Scenario: Пользователь вызывает API лаборатории без допуска
- **WHEN** клиент или внешний вызов обращается к API лаборатории без успешной проверки допуска
- **THEN** система отклоняет запрос и не выполняет основную бизнес-логику

### Requirement: Нормализация email фиксирована

Система SHALL нормализовать email одинаково при вычислении allowlist-маркера:
- удалять пробелы по краям;
- переводить строку в lowercase.

#### Scenario: Пользователь вводит email в смешанном регистре
- **WHEN** пользователь вводит email с заглавными буквами и лишними пробелами
- **THEN** система проверяет допуск по нормализованному значению

### Requirement: Модель допуска не считается подтверждением владения email

Система SHALL трактовать allowlist-проверку как gatekeeping по email, а не как подтверждение того, что пользователь владеет почтовым ящиком.

#### Scenario: Система успешно нашла allowlist-маркер
- **WHEN** allowlist-маркер найден
- **THEN** система считает только то, что введённый email допущен, но не считает email подтверждённым
