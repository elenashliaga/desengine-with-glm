## Context

Продукт остаётся local-first: пользователь работает в локальной лаборатории, а удалённый слой нужен только для управления списком допуска. Писать отдельный auth backend сейчас не хочется. Также нежелательно передавать полный список email по сети даже в зашифрованном виде.

## Goals / Non-Goals

**Goals:**
- Впустить в систему только пользователя с email из удалённо управляемого allowlist.
- Не скачивать список целиком.
- Не публиковать raw email на сервере в открытом виде.
- Сохранить схему максимально дешёвой и без собственного auth backend.
- Требовать новую проверку доступа при каждом новом открытии приложения.
- Закрыть без допуска не только UI, но и прямой доступ к маршрутам и API лаборатории.

**Non-Goals:**
- Подтверждение владения email.
- Полноценная identity/auth система.
- Роли, группы, разграничение прав внутри продукта.
- Защита от целенаправленного реверс-инжиниринга клиента.
- Долговременная пользовательская сессия между открытиями приложения.

## Decisions

- Модель допуска: один удалённый маркер на один разрешённый email.
  - Клиент не скачивает список целиком.
  - Клиент проверяет существование одного конкретного ресурса.

- Идентификатор маркера: salted hash от нормализованного email.
  - Формула на MVP: `sha256(normalizedEmail + ":" + salt)`.
  - Альтернатива: raw email в URL.
  - Выбранный вариант лучше скрывает allowlist от прямого просмотра.

- Нормализация email должна быть строгой и одинаковой на стороне подготовки allowlist и в клиенте.
  - На MVP: trim, lowercase.
  - Локальная часть email не преобразуется сверх этого.

- Проверка допуска выполняется по HTTP(S) GET или HEAD к удалённому URL вида:
  - `<baseUrl>/<hash>`
  - `200` означает “доступ разрешён”
  - `404` означает “доступ запрещён”
  - остальные ошибки считаются техническими

- Успешный допуск живёт только в рамках текущего открытия приложения.
  - После полного закрытия приложения или новой загрузки страницы пользователь вводит email заново.
  - На MVP не сохраняем допуск в локальное хранилище, файл или долгоживущий cookie.

- Защита реализуется на серверной стороне для всего `lab`.
  - Страницы лаборатории не должны рендериться как доступные без успешной проверки.
  - Все API-маршруты лаборатории должны проверять факт допуска до выполнения основной логики.
  - Клиентский экран ввода email рассматривается только как UX-слой поверх серверного gatekeeping.

- Состояние допуска на MVP может храниться только как краткоживущая серверная сессия текущего открытия.
  - Конкретный носитель (например, cookie текущей сессии) выбирается при реализации.
  - Контракт важнее механизма: после нового открытия доступ не восстанавливается автоматически.

- Salt хранится в приложении как конфигурационный секрет сборки.
  - Это не идеальная защита, но достаточная для выбранного класса задачи.
  - Salt не публикуется рядом с allowlist-маркерами.

## Risks / Trade-offs

- [Не подтверждается владение почтой] → любой, кто знает разрешённый email, может попробовать войти под ним → это осознанное ограничение MVP.
- [Salt извлекаем из клиента] → схема скрывает allowlist от случайного просмотра, но не защищает от мотивированного реверс-инжиниринга → приемлемо для текущего масштаба.
- [Зависимость от сети] → без доступа к allowlist-серверу нельзя проверить допуск → потребуется UX для сетевых ошибок и, возможно, локальный кэш решения позже.
- [Нет сохранения допуска между открытиями] → пользователь вводит email чаще → это осознанный компромисс ради простоты MVP и минимального хранения состояния.
- [Только UI-защиты недостаточно] → пользователь может вызвать API напрямую → поэтому защита должна проверяться на сервере для каждого маршрута лаборатории.
- [Нормализация должна совпадать] → несовпадение правил нормализации сломает доступ корректным пользователям → нормализацию нужно формально зафиксировать в спеке.
