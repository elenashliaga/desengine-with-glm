## Status

Suspended.

После пересмотра LLM-стратегии change временно выведён из активного планирования.

Причина не только в качестве фактического результата, но и в сегодняшнем продуктовом решении: основной поток `lab` поддерживает только сетевые провайдеры по ключу.

## Context

Сейчас система жёстко завязана на облачный ChatGPT API по ключу. Это противоречит local-first направлению продукта: пользователь работает локально, задачи лежат локально, и логично уметь подключать модель, доступную либо на той же машине, либо в локальной сети. При этом продукту не нужен “зоопарк” интеграций на первом этапе: первым локальным адаптером должен стать именно Ollama.

## Goals / Non-Goals

**Goals:**
- Ввести единый LLM-слой, через который проходят старт задачи и обычные итерации.
- Поддержать как минимум два режима подключения: облачный по ключу и Ollama по URL.
- Зафиксировать минимальную конфигурацию Ollama и требования к её проверке.
- Подготовить архитектуру к будущим локальным адаптерам, не реализуя их сейчас.

**Non-Goals:**
- Немедленная реализация поддержки всех возможных локальных LLM-серверов.
- Универсальный стандарт обмена для любого LLM API на рынке.
- Автоматическое обнаружение моделей в локальной сети.
- Полный отказ от облачного сценария на этом этапе.

## Decisions

- В продукте появляется режим подключения LLM, задаваемый конфигурацией.
  - Минимум два значения: облачный провайдер по ключу и Ollama по URL.
  - Это позволяет не зашивать выбор провайдера в конкретные route handler'ы.

- Ollama описывается URL-ориентированной конфигурацией.
  - Минимально фиксируются: базовый URL, имя модели и таймаут.
  - Тип адаптера в этом change не является переменной пользователя: он фиксирован как `ollama`.
  - Причина: для первого локального сценария нам нужна рабочая конкретика, а не общий конструктор под всё подряд.

- Старт задачи и обычная итерация используют один и тот же абстрактный контракт “LLM-вызова”.
  - Отличаются только входные промпты и набор файлов, но не способ подключения к провайдеру.
  - Это уменьшает расхождения между `/start` и `/iterate`.

- Проверка доступности Ollama считается отдельным поведением системы.
  - Нельзя сводить всё к “упало при реальном запросе”.
  - Пользователь должен видеть, что именно не так: не задан URL, узел недоступен, таймаут, неподдерживаемый формат ответа.

- На MVP первый локальный адаптер фиксируется как Ollama.
  - Другие локальные системы будут добавляться отдельными change'ами как отдельные адаптеры.
  - Это позволяет не смешивать в одном change разные протоколы и разные требования к форматам запросов/ответов.

- Учёт затрат/метрик зависит от возможностей провайдера.
  - Для облачного провайдера сохраняется текущая модель затрат.
  - Для Ollama отсутствие денежных метрик допустимо; система не должна выдумывать стоимость, если провайдер её не возвращает.

## Risks / Trade-offs

- [Слишком абстрактный слой] → можно переусложнить MVP множеством адаптеров → на первом этапе нужен один конкретный адаптер: Ollama.
- [Специфика протокола Ollama] → интеграция всё равно будет зависеть от конкретного формата API → это допустимо, потому что другие системы пойдут отдельными change'ами.
- [Сетевые ошибки внутри LAN] → пользователь будет чаще сталкиваться с таймаутами и недоступностью узла → нужны понятные диагностические сообщения и явная проверка доступности.
- [Разные возможности по метрикам] → данные о токенах/стоимости могут стать несопоставимыми → система должна различать “метрики есть” и “метрик нет”, а не подменять одно другим.
