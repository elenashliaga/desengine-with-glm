## Context

Сейчас initiator-поток уже выделен как отдельное действие продукта с `target: "init"`, но после `simplify-llm-flow` он использует тот же активный провайдер и ту же модель, что и обычные уточнения. Исторически медленный путь был замечен на OpenAI, но сама проблема относится к initiator-классу запросов вообще: скрытый старт уровня остаётся самым тяжёлым пользовательски значимым LLM-вызовом в обычном потоке работы.

Текущий init-запрос тяжёлый по нескольким причинам:
- он несёт длинный объединённый instruction с production-, didactic- и level-specific частями;
- он всегда включает все level-разрешённые PNG-картинки уровня как base64;
- для перехода на новый уровень он дополнительно может включать все текущие текстовые файлы;
- у initiator-пути всё ещё нет отдельного таймаута и нет явного latency-budget как продуктового контракта.
- наблюдаемость уже частично добавлена: сервер логирует старт, длительность, размер instruction, число картинок, ответ провайдера, parse-сбои и успешную запись файлов.

## Goals / Non-Goals

**Goals:**
- Уменьшить среднюю и хвостовую задержку initiator-запроса старта уровня.
- Сделать структуру init-входа более компактной и менее дублирующейся.
- Ввести отдельный timeout и диагностический контракт для initiator-потока.
- Сохранить текущий функциональный результат: старт уровня по-прежнему возвращает полный набор файлов задачи.

**Non-Goals:**
- Смена активного LLM-провайдера в рамках этого change.
- Полный пересмотр didactic-материалов уровней.
- Перевод initiator-потока на streaming UI.
- Гарантия конкретного значения latency без последующей реализации и измерения.

## Decisions

- Initiator-поток оптимизируется как отдельный класс вызова, а не как побочный эффект общей чистки LLM-слоя.
  - Причина: обычные уточняющие промпты и скрытый старт уровня имеют разную структуру нагрузки и разные UX-ожидания.

- Система должна минимизировать избыточный init-контекст.
  - Нельзя дублировать одну и ту же инструкцию в нескольких промпт-слоях, если это не влияет на качество.
  - Для первого входа в задачу нельзя отправлять “текущее состояние всех файлов”, если этих файлов ещё нет.
  - Для перехода на новый уровень нужно отправлять только тот набор файлов, который реально нужен для продолжения работы на новом уровне.

- Для initiator-потока фиксируется отдельный timeout.
  - Если активный провайдер не успевает ответить в отведённое время, система должна прервать вызов и вернуть понятную retriable-ошибку.
  - Timeout должен настраиваться отдельно от обычных итераций, потому что у initiator-потока свои требования к входу и latency-budget, хотя модель остаётся общей.

- Для initiator-потока фиксируется отдельная наблюдаемость.
  - Базовый безопасный диагностический след уже существует и не должен быть потерян при дальнейших правках.
  - Минимальный диагностический след: `taskId`, provider, model, target, число картинок, длина instruction, длительность вызова, длина ответа, исход (`success`, `timeout`, `provider_error`, `parse_error`, `write_error`).
  - Секреты, raw API key и полный текст пользовательских данных в логах недопустимы.

- Оптимизация должна быть измеряемой.
  - До и после реализации нужно сравнить хотя бы локально: полную длительность `/start`, длительность LLM-вызова и успешность разбора JSON-ответа.
  - Change считается успешным только если ускорение не ломает контракт генерации пяти рабочих файлов.

## Risks / Trade-offs

- [Слишком агрессивное сокращение промпта] → можно ускорить запрос ценой ухудшения качества стартовых файлов → нужно отделять обязательный контекст от декоративного, а не просто “резать всё подряд”.
- [Жёсткий timeout] → система начнёт чаще падать в пограничных сетевых условиях → timeout должен быть отдельным и осознанно подобранным для initiator-потока.
- [Слишком подробные логи] → можно случайно залогировать лишние данные о задаче → логировать только агрегаты и короткие preview там, где это действительно нужно для диагностики.
- [Локальная оптимизация без продуктовой цели] → можно улучшить один конкретный taskId, но не общий поток → измерения и acceptance criteria должны относиться к initiator-потоку в целом.

## Open Questions

- Нужен ли отдельный env var для timeout initiator-потока или достаточно общего cloud-timeout с override для `init`?
- Нужно ли вводить отдельный “compact init prompt” как явный файл prompt-контракта, или достаточно перестроить уже существующую сборку instruction?
- Достаточно ли отдельного timeout и сокращения контекста, или позже понадобится дополнительный latency-budget без возврата к отдельной init-модели?
