## Context

Сейчас в проекте уже зафиксированы два соседних контракта:
- `desengine.config.txt` хранит `DESENGINE_ONBOARDING_REPO_URL`;
- `/config` даёт ручное действие `Обновить onboarding`.

Этого достаточно для ручной эксплуатации, но недостаточно для надёжной первичной установки. Пользователь может получить локальный проект с уже существующим `/onboarding`, не загрузить его вовсе или загрузить вручную позже из другого источника. В таком состоянии шаблонная конфигурация и фактический контент расходятся, а установка формально выглядит рабочей.

## Goals / Non-Goals

**Goals:**
- Сделать шаблонный `DESENGINE_ONBOARDING_REPO_URL` реальным источником первичной загрузки `/onboarding`.
- Гарантировать, что официальная установка не считается готовой без синхронизации `/onboarding` с этим репозиторием.
- Явно диагностировать mismatch между настроенным репозиторием и фактическим локальным `/onboarding`.
- Сохранить существующий ручной сценарий повторного обновления через `/config`.

**Non-Goals:**
- Вводить фоновую автосинхронизацию onboarding-контента.
- Менять формат локального конфига, стек запуска или механизм хранения Git в репозитории.
- Разрешать fallback на произвольный локальный `/onboarding` без подтверждённого источника.

## Decisions

### 1. Первичная загрузка становится частью официальной установки

Официальный install-flow должен либо сам выполнять первичную синхронизацию `/onboarding`, либо явно останавливать сценарий готовности, пока эта синхронизация не выполнена. Наличие одного только `DESENGINE_ONBOARDING_REPO_URL` в шаблоне больше не считается достаточным.

Альтернатива: оставить первичную загрузку полностью ручной через `/config`.
Почему не она: это сохраняет текущий баг, при котором шаблонные настройки не гарантируют фактический источник локального контента.

### 2. Источник первичной загрузки определяется конфигурацией, а не локальным остатком каталога

Канонический источник `/onboarding` для новой установки определяется значением `DESENGINE_ONBOARDING_REPO_URL`, пришедшим из шаблонной конфигурации и затем попавшим в `desengine.config.txt`. Если локально уже лежит каталог `/onboarding`, система должна проверить, что он согласован с этим источником, а не молча принимать его как валидный.

Альтернатива: считать существующий каталог `/onboarding` достаточным без проверки происхождения.
Почему не она: это не даёт гарантии, что установка использует именно тот репозиторий, который обещан шаблоном.

### 3. Диагностика должна различать отсутствие, рассинхрон и корректную синхронизацию

Сценарий проверки готовности должен разделять как минимум три состояния:
- `/onboarding` отсутствует;
- `/onboarding` существует, но не подтверждён как загруженный из настроенного репозитория;
- `/onboarding` синхронизирован из репозитория, указанного в конфигурации.

Для этого реализации может понадобиться локальный маркер последней успешной синхронизации с адресом репозитория или эквивалентная проверка происхождения. В design фиксируется требование на различение состояний, а не конкретный формат хранения.

Альтернатива: проверять только наличие каталога.
Почему не она: каталог может быть чужим, устаревшим или перенесённым вручную.

### 4. Ручное обновление остаётся повторной операцией

Кнопка `Обновить onboarding` на `/config` сохраняется как явный способ переподтянуть контент после установки или после смены `DESENGINE_ONBOARDING_REPO_URL`. Но она больше не должна быть единственной дорожкой, через которую система впервые приходит к корректному состоянию.

## Risks / Trade-offs

- [Проверка происхождения `/onboarding`] → потребуется хранить или вычислять дополнительный признак синхронизации → смягчается тем, что spec не навязывает конкретный формат метаданных.
- [Более строгий install-flow] → установка может чаще останавливаться с ошибкой готовности → это осознанная цена за предсказуемый источник контента.
- [Старые локальные окружения] → существующие каталоги `/onboarding` могут начать считаться неподтверждёнными → нужен явный migration/repair path через первичную синхронизацию или ручное обновление.
