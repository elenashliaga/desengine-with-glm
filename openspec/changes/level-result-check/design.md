## Context

Текущий поток завершения уровня слишком прямолинеен:
- кнопка `Я закончил` сразу переводит уровень в `completed`;
- пользователь попадает на экран перехода к следующему уровню без проверки результата;
- в progress model нет места для попыток проверки, результата проверки и технических сбоев этой проверки.

При этом уже есть несколько связанных решений:
- уровень имеет allowlist рабочих файлов через `editableFileIds`;
- didactic prompts уровня постепенно выносятся в `onboarding/prompts/levels/<levelId>/`;
- task flow всё больше строится как набор явных фаз уровня, а не как один непрерывный экран.

Новая проверочная фаза должна встроиться в эту модель без смешения:
- hidden checking prompt относится к скрытому onboarding prompt-слою;
- пользовательский экран результата проверки не становится частью истории задачи;
- технический сбой проверки не должен искажать прогресс задачи;
- последняя допустимая неуспешная проверка должна сбрасывать задачу полностью, но не ломать UX result-экрана.

## Goals / Non-Goals

**Goals:**
- Ввести для каждого уровня явную LLM-проверку результата перед завершением уровня.
- Сделать `Я закончил` действием запуска проверки, а не мгновенного завершения.
- Зафиксировать hidden checking prompt уровня.
- Зафиксировать limit-политику проверок и сброс задачи при исчерпании допустимых проверок.
- Зафиксировать одноразовую страницу результата проверки с разными сценариями:
  - успешная проверка;
  - неуспешная проверка с оставшимися попытками;
  - технический сбой;
  - неуспешная последняя проверка со сбросом задачи.

**Non-Goals:**
- Переработка качества самих didactic-условий уровней.
- Введение отдельной второй модели или отдельного провайдера именно для проверки.
- Долговременная история всех страниц результатов проверки в пользовательском интерфейсе.

## Decisions

- Для каждого уровня вводится отдельный hidden checking prompt.
  - Канонический путь: `onboarding/prompts/levels/<levelId>/check.md`.
  - Этот prompt относится к скрытому onboarding prompt-слою и не отображается пользователю.

- Настройка лимита проверок уровня хранится в открытом конфиге уровня.
  - Поле: `maxCheckAttempts`.
  - Путь: `onboarding/levels/<levelId>/config.json`.
  - Это короткая структурированная настройка уровня, поэтому ей место в `config.json`.

- Кнопка `Я закончил` больше не завершает уровень напрямую.
  - Она запускает checking run.
  - После любого ответа checking flow пользователь уходит на отдельную страницу результата проверки.

- Проверка использует тот же уровень контекста, что и пользовательская работа, плюс hidden checking prompt.
  - В checking run входят:
    - все рабочие файлы из `editableFileIds` текущего уровня;
    - все level-разрешённые картинки текущего уровня;
    - hidden checking prompt уровня;
    - открытое пояснение уровня и task-specific пояснение уровня, если они уже входят в дидактический контур уровня;
    - production prompt-контур, если он нужен текущему LLM API contract.
  - Отдельного специального file-allowlist для проверки не вводится.

- Ответ checking run должен быть структурированным.
  - Минимально система должна получать:
    - `passed: boolean`;
    - `message: string`.
  - `message` предназначен для пользовательской страницы результата проверки.

- Успешная проверка сразу завершает уровень.
  - Как только checking run вернул содержательный успех с `passed = true`, уровень считается завершённым.
  - Пользователь на result-экране уже видит результат завершённого уровня и может пойти дальше.
  - Отдельное второе подтверждение “завершить уровень” не требуется.

- Исчерпание лимита уточняющих промптов само по себе больше не завершает уровень.
  - Если пользователь израсходовал `maxPromptsPerTask`, система только блокирует новый `iterate`.
  - Уровень остаётся не завершённым, пока не пройдена успешная проверка.
  - Старое правило “prompt limit => completed” считается отменённым этим change.

- Неуспешная содержательная проверка не завершает уровень.
  - Пользователь попадает на result-экран.
  - Если лимит проверок ещё не исчерпан, с этого экрана можно только вернуться в лабораторию.

- Технический сбой проверки не считается попыткой проверки.
  - Если checking run не состоялся из-за сетевой ошибки, ошибки провайдера или невалидного ответа, задача не получает содержательную попытку проверки.
  - Пользователь видит result-экран с сообщением о техническом сбое.
  - С этого экрана доступно действие `Повторить проверку`.
  - Статус задачи/уровня в таком сценарии трактуется как `Ждёт проверки`.

- Лимит `maxCheckAttempts` считает только содержательные ответы проверки.
  - В счётчик входят только ответы, где система реально получила валидный `passed / not passed`.
  - Технические сбои туда не входят.

- Последняя допустимая неуспешная проверка сбрасывает задачу целиком.
  - Если неуспешная содержательная проверка исчерпала `maxCheckAttempts`, система сбрасывает задачу так, будто она не начиналась.
  - При этом система сохраняет одноразовый ephemeral-результат последней проверки, чтобы result-page могла объяснить, что произошло.
  - Этот ephemeral-результат не считается частью долгоживущего task progress.

- Страница результата проверки одноразовая.
  - Она показывает только последний checking outcome.
  - Она не обязана становиться отдельной историей внутри задачи.
  - После ухода с неё система не обязана поддерживать повторное открытие старого результата как пользовательский архив.

- Канонический route результата проверки фиксируется отдельно от route перехода между уровнями.
  - Для user-facing URL вводится path-based маршрут `/tasks/<taskId>/check`.
  - `/tasks/<taskId>/next` остаётся экраном перехода уже после успешного завершения уровня.

- Экран перехода `/tasks/<taskId>/next` должен быть содержательным, а не только навигационным.
  - После успешной проверки пользователь видит:
    - что именно было достигнуто на только что завершённом уровне;
    - актуальную демку/результат этого уровня;
    - чего ожидает следующий уровень.
  - По смыслу этот экран должен собирать narrative вида:
    - “мы решили такую-то задачу на предыдущем уровне”;
    - “вот как это сейчас выглядит”;
    - “а теперь хотим следующего качества/следующего шага уровня”.
  - Формулировка предыдущего шага должна опираться на материалы завершённого уровня.
  - Формулировка следующего шага должна опираться на открытые материалы следующего уровня.

## Data Model Notes

- Level config получает новое поле:
  - `maxCheckAttempts: number`

- Progress model уровня должна уметь хранить:
  - число содержательных проверок на текущем уровне;
  - признак того, что уровень ждёт успешной проверки после технического сбоя;
  - краткое состояние последней содержательной проверки, если оно нужно для текущего flow.

- Отдельно от основного progress нужен ephemeral check result.
  - Он нужен, чтобы пережить автоматический reset после последней неуспешной проверки.
  - Он должен содержать минимум:
    - `taskId`;
    - `levelId`;
    - `attemptNumber`;
    - `passed`;
    - `message`;
    - `kind` (`passed` / `failed` / `technical_error` / `failed_and_reset`);
    - timestamp.

## Pre-Implementation Checklist

- Проинвентаризировать все места, где `Я закончил` сейчас вызывает прямой `complete`.
- Проинвентаризировать все места, где исчерпание `maxPromptsPerTask` автоматически завершает уровень.
- Проверить текущий `TaskTransition` flow и решить, где именно checking result переходит в `/next`.
- Зафиксировать, какие открытые level-материалы используются для narrative экрана `/next`.
- Добавить в onboarding layout `check.md` для уровней.
- Обновить level config schema под `maxCheckAttempts`.
- Спроектировать structured schema checking-ответа LLM.
- Отдельно продумать lifecycle ephemeral check result после успешной навигации пользователя со страницы `/tasks/<taskId>/check`.
- Проверить совместимость change с `per-level-start-pages`, чтобы новый уровень после успешной проверки переходил в состояние “текущий, но ещё не начат”.

## Risks / Trade-offs

- [Сброс после последней неудачи] → если сразу стереть весь task state без отдельного ephemeral результата, пользователь потеряет объяснение, почему всё сбросилось → нужен отдельный одноразовый слой результата проверки.
- [Смешение checking и completion] → легко случайно оставить старую логику, где ручное завершение минует проверку → change должен прямо запретить прямой `complete` по кнопке `Я закончил`.
- [Legacy prompt-limit completion] → легко оставить старую автологику завершения по лимиту промптов и тем самым обойти новую фазу проверки → реализация должна явно разорвать эту связь.
- [Нечёткие статусы уровня] → текущих `available / in_progress / completed` недостаточно для прозрачного UX проверки → реализация должна либо расширить статусную модель, либо добавить связанный check-state слой, но без двусмысленности.
- [Технические сбои] → если считать их попытками, UX станет несправедливым → спецификация прямо исключает их из лимита.
- [Открытый текст результата] → LLM может вернуть слишком длинное или слабоструктурированное объяснение → checking schema должна ограничивать и формализовать пользовательское сообщение.
