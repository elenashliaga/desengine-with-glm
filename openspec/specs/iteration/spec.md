# Итерация (LLM-запуск)

Итерация — основной цикл работы пользователя с заданием.

## Purpose

Определить контракт “одного шага работы” с LLM: что считается входом итерации, что считается её результатом, и как система ведёт себя при ошибках.

## Requirements

### Requirement: Итерация использует обязательные входные данные

Система SHALL включать в каждую итерацию:
- все картинки, которые разрешено показывать пользователю на текущем уровне задачи;
- текущий промпт пользователя,
- все рабочие файлы, разрешённые на текущем уровне,
- системные промпты (производственные; дидактические уровня — только в обучающем режиме),
- явный список рабочих файлов, которые разрешено вернуть как результат на текущем уровне.

#### Scenario: Пользователь запускает уточняющий промпт
- **WHEN** пользователь запускает итерацию
- **THEN** система включает в контекст итерации все рабочие файлы, разрешённые на текущем уровне
- **AND** все level-разрешённые картинки текущего уровня

#### Scenario: Пользователь запускает обычное уточнение после старта
- **WHEN** задача уже инициализирована и пользователь отправляет уточняющий промпт
- **THEN** система снова отправляет все картинки, которые разрешено показывать пользователю на текущем уровне задачи
- **AND** использует текстовый контекст из всех рабочих файлов, разрешённых на текущем уровне
- **AND** включает общее пояснение уровня в prompt итерации

#### Scenario: У уровня есть task-specific tip
- **WHEN** система формирует prompt для `start`, `iterate` или `check`
- **AND** для текущего уровня существует `onboarding/tasks/<taskId>/levels/<levelId>/tip.md`
- **THEN** она не включает этот `tip.md` автоматически в LLM prompt-контекст

#### Scenario: Система собирает текст итерационного промпта
- **WHEN** система формирует итоговый промпт для `iterate`
- **THEN** она явно перечисляет разрешённые файлы результата текущего уровня в тексте этого промпта

### Requirement: Инициирующий запуск уровня использует картинку и все файлы

Система SHALL выполнять скрытый инициирующий запуск каждого уровня с level-разрешёнными картинками задачи, полным набором рабочих файлов текущего уровня и системными промптами уровня.

#### Scenario: Система инициирует новый уровень
- **WHEN** пользователь впервые входит в уровень задачи
- **THEN** система отправляет все level-разрешённые картинки задачи
- **AND** отправляет все рабочие файлы, разрешённые на этом уровне
- **AND** использует производственный и дидактический промпты уровня

#### Scenario: Система собирает текст инициирующего промпта
- **WHEN** система формирует итоговый промпт для `start`
- **THEN** она явно перечисляет разрешённые файлы результата текущего уровня в тексте этого промпта

#### Scenario: Модель не заполнила служебный файл уровня
- **WHEN** скрытый инициирующий запуск возвращает пустой контент для `styles.ts`, `mock.ts` или `props.ts`
- **THEN** система не срывает инициацию уровня только из-за этого
- **AND** сохраняет существующий контент файла, если он уже был
- **AND** иначе подставляет безопасную каноническую заготовку

### Requirement: Инициирующий запуск не считается уточняющим промптом

Система SHALL не включать скрытый инициирующий запуск уровня в список уточняющих промптов пользователя и не учитывать его в лимите `maxPromptsPerTask`.

Reset задачи SHALL полностью очищать историю уточняющих промптов этой задачи.

#### Scenario: Пользователь смотрит на историю уточняющих промптов
- **WHEN** система уже выполнила инициирующий запуск уровня
- **THEN** этот запуск не показывается в списке уточнений
- **AND** не уменьшает остаток уточняющих промптов уровня

#### Scenario: Пользователь сбрасывает задачу
- **WHEN** reset задачи завершён
- **THEN** история уточняющих промптов этой задачи становится пустой

### Requirement: Уточняющий промпт использует composer-поле с автоподрастанием

Система SHALL использовать для уточняющего промпта composer-поле, которое в исходном состоянии вмещает одну строку и автоматически растёт по вертикали по мере ввода многострочного текста.

#### Scenario: Пользователь начинает вводить короткое уточнение
- **WHEN** пользователь открывает composer уточняющего промпта
- **THEN** поле ввода отображается в однострочном стартовом состоянии

#### Scenario: Пользователь вводит многострочный текст
- **WHEN** пользователь добавляет переносы строки или текст перестаёт помещаться в одну строку
- **THEN** composer-поле автоматически увеличивается по вертикали

### Requirement: Уточняющий промпт поддерживает keyboard-submit

Система SHALL поддерживать клавиатурную отправку уточняющего промпта и отдельную комбинацию для ручного переноса строки.

#### Scenario: Пользователь нажимает Enter в непустом поле
- **WHEN** composer доступен для ввода
- **AND** поле содержит непустой текст
- **AND** пользователь нажимает `Enter`
- **THEN** система отправляет уточняющий запрос

#### Scenario: Пользователь нажимает Enter в пустом поле
- **WHEN** composer доступен для ввода
- **AND** поле не содержит текста для отправки
- **AND** пользователь нажимает `Enter`
- **THEN** система не отправляет пустой запрос
- **AND** показывает понятную ошибку в composer

#### Scenario: Пользователь нажимает Shift+Enter
- **WHEN** composer доступен для ввода
- **AND** пользователь нажимает `Shift+Enter`
- **THEN** в поле вставляется перенос строки
- **AND** запрос не отправляется

### Requirement: Кнопка запуска встроена в composer-ряд

Система SHALL размещать кнопку `Запустить →` справа от composer-поля в одном нижнем ряду ввода.

#### Scenario: Пользователь видит composer уточняющего промпта
- **WHEN** task-экран отображает нижний composer
- **THEN** кнопка `Запустить →` находится справа от поля ввода
- **AND** остаётся доступной как альтернативный способ отправки

#### Scenario: Скрытый инициирующий запуск уровня ещё не завершён
- **WHEN** пользователь нажимает кнопку `Запустить →` или клавишу `Enter`
- **AND** скрытый инициирующий запуск текущего уровня ещё не завершён
- **THEN** система не отправляет итерационный запрос
- **AND** показывает понятное сообщение о необходимости дождаться инициирующего запуска

### Requirement: Инициирующий запуск и уточнения используют одну модель

Система SHALL использовать одну и ту же модель для скрытого инициирующего запуска и для обычных уточняющих запросов.

#### Scenario: Система выполняет инициирующий запуск уровня
- **WHEN** система выполняет инициирующий запуск уровня
- **THEN** она использует ту же модель, что и для обычных уточняющих промптов

### Requirement: Итерация возвращает обновлённые версии файлов

Система SHALL возвращать результат итерации как обновлённые версии файлов набора (возможно, изменены не все).

#### Scenario: Модель изменила только часть файлов
- **WHEN** итерация вернула изменения только для части файлов
- **THEN** остальные файлы остаются без изменений

### Requirement: Итерация не может создать запрещённый для уровня рабочий файл

Система SHALL применять результат итерации только к тем рабочим файлам, которые разрешены на текущем уровне.

#### Scenario: LLM вернул запрещённый `fileId`
- **WHEN** ответ LLM содержит рабочий файл, который не входит в allowlist текущего уровня
- **THEN** система игнорирует этот результат
- **AND** не создаёт и не обновляет соответствующий файл на диске

### Requirement: Ошибка итерации не разрушает текущее состояние

Система SHALL сохранять текущее состояние задания при ошибке LLM (сеть/лимиты/невалидный ответ) и позволять повторить итерацию.

#### Scenario: Провайдер вернул ошибку
- **WHEN** провайдер LLM вернул ошибку
- **THEN** система не теряет текущее состояние файлов и показывает пользователю понятное сообщение

### Requirement: Итерация учитывает лимит промптов уровня

Система SHALL разрешать новую итерацию только пока пользователь не исчерпал `maxPromptsPerTask` текущего уровня задачи.

#### Scenario: Лимит текущего уровня ещё не исчерпан
- **WHEN** число использованных промптов меньше лимита текущего уровня
- **THEN** система разрешает новую итерацию

#### Scenario: Лимит текущего уровня исчерпан
- **WHEN** число использованных промптов равно лимиту текущего уровня
- **THEN** система не запускает новую итерацию
- **AND** не завершает уровень автоматически
- **AND** сохраняет возможность пройти отдельную проверку результата уровня

### Requirement: История уточняющих запросов показывает учебный контекст итераций

Система SHALL хранить и показывать историю уточняющих запросов в порядке выполнения: от первого к последнему.

Для каждого уточняющего запроса система SHALL показывать:
- его порядковый номер в рамках задачи;
- дату и время в формате `YYYY-MM-DD HH:mm:ss`;
- список файлов, отправленных в контекст текущей итерации;
- список файлов, реально изменённых результатом итерации;
- кнопку копирования текста запроса;
- учебную стоимость запроса.

#### Scenario: Пользователь открывает историю уточнений
- **WHEN** у задачи есть несколько выполненных уточняющих запросов
- **THEN** система показывает сначала самый ранний запрос, а затем все последующие

#### Scenario: Пользователь просматривает карточку ранее выполненного уточнения
- **WHEN** пользователь открывает запись в истории уточнений
- **THEN** система показывает текст запроса, дату в формате `YYYY-MM-DD HH:mm:ss`, отправленные файлы и реально изменённые файлы
- **AND** рядом с текстом есть кнопка `Скопировать`

### Requirement: Учебная стоимость уточнений считается по фиксированной ставке

Система SHALL считать условную стоимость каждого уточняющего запроса равной 3 центам и SHALL показывать суммарную стоимость по задаче как отдельный учебный индикатор.

Этот индикатор SHALL быть отделён от реальных токеновых или денежных метрик LLM-провайдера и SHALL не подменять их.

#### Scenario: Пользователь выполнил несколько уточнений
- **WHEN** у задачи сохранено `N` уточняющих запросов
- **THEN** система показывает суммарную стоимость `N * 3` цента
- **AND** эта ставка не зависит от модели, размера ответа или других параметров

#### Scenario: Провайдер не вернул реальные метрики
- **WHEN** у итерации нет токеновых или денежных метрик от LLM-провайдера
- **THEN** учебный индикатор стоимости всё равно отображается отдельно
- **AND** интерфейс не выдаёт его за реальные метрики провайдера

### Requirement: Дидактические промпты итерации приходят из onboarding-репозитория

Система SHALL считать onboarding-репозиторий каноническим источником didactic-промптов, используемых при уровне и итерациях.

#### Scenario: Система формирует didactic-часть промпта
- **WHEN** система добавляет didactic-промпт к `start` или `iterate`
- **THEN** она использует onboarding-репозиторий как источник этого промпта

### Requirement: Production-промпты итерации остаются в основном репозитории

Система SHALL считать production-промпты частью основного репозитория продукта.

#### Scenario: Система формирует production-часть промпта
- **WHEN** runtime нужен production-промпт
- **THEN** система читает его из основного репозитория

## Основной принцип

Пользователь ожидает, что за один запуск LLM система способна изменить **несколько файлов** в пределах рабочего набора, разрешённого на текущем уровне.

## Вход итерации

Итерация должна учитывать:
- все картинки, которые разрешено показывать пользователю на текущем уровне задачи;
- текущий промпт пользователя;
- все рабочие файлы набора, разрешённые на текущем уровне;
- явный список разрешённых файлов результата текущего уровня;
- системные промпты (производственные; дидактические — только в обучающем режиме).
- системные промпты (производственные; дидактические конкретного уровня — только в обучающем режиме).

## Выход итерации

Итерация возвращает обновлённые версии файлов набора.

## Ошибки и обратная связь

При ошибках LLM (сеть/лимиты/невалидный ответ) система:
- не теряет текущее состояние файлов;
- показывает пользователю понятное сообщение;
- позволяет повторить итерацию после исправления причины.
