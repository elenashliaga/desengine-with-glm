# Задание (Task)

Задание — единица работы пользователя в лаборатории: это “что нужно реализовать”, где лежат project-owned исходные данные и где хранится текущее пользовательское состояние.

## Purpose

Определить минимальную модель задания: что обязательно должно существовать, чтобы пользователь мог выполнять итерации и получать/публиковать результат.

## Requirements

### Requirement: PNG-картинки обязательны для задания на MVP

Система SHALL требовать хотя бы одну PNG‑картинку компонента как обязательную часть задания.

#### Scenario: Пользователь пытается запустить итерацию без PNG-картинок
- **WHEN** у задания отсутствуют PNG-картинки
- **THEN** система не может выполнить инициирующий запуск задания и сообщает об ошибке

### Requirement: Задание включает текущее состояние файлов

Система SHALL хранить текущее состояние набора файлов компонента в user-owned рабочем состоянии задачи и SHALL показывать список всех задач на стартовой странице пользователя.

Редактирование этих файлов в лаборатории SHALL происходить через полноценный кодовый редактор с подсветкой синтаксиса, а не через plain textarea.
Система SHALL автоматически сохранять только реально изменённые файлы и явно показывать несохранённое состояние до момента успешной записи.
Рабочий экран задачи SHALL оставаться task-specific workspace без технических подписей у preview и без дублирования общего описания уровня рядом с task-specific деталями.

#### Scenario: Пользователь возвращается к заданию позже
- **WHEN** пользователь открывает ранее начатое задание
- **THEN** система показывает текущее состояние файлов из user-owned рабочего состояния задачи

#### Scenario: Пользователь открывает редактируемый файл
- **WHEN** пользователь выбирает файл задачи в лаборатории
- **THEN** система открывает его в полноценном кодовом редакторе
- **AND** показывает содержимое файла с синтаксической подсветкой

#### Scenario: Пользователь меняет содержимое файла
- **WHEN** пользователь изменил содержимое активного файла
- **THEN** система помечает этот файл как несохранённый
- **AND** запускает автосохранение не раньше чем через 10 секунд после последнего изменения

#### Scenario: Пользователь ничего не менял после последнего сохранения
- **WHEN** содержимое файла не изменялось с момента последней успешной записи
- **THEN** система не выполняет повторное сохранение этого файла

#### Scenario: Пользователь редактирует активный файл с несохранёнными изменениями
- **WHEN** активный файл содержит несохранённые изменения
- **THEN** редактор этого файла получает красную рамку
- **AND** вкладка этого файла показывает заметную красную точку

#### Scenario: Пользователь запускает явное сохранение
- **WHEN** у задачи есть несколько несохранённых файлов
- **AND** пользователь нажимает кнопку `Сохранить`, `Cmd+S` или `Ctrl+S`
- **THEN** система сохраняет все несохранённые файлы одним действием
- **AND** после успешного сохранения скрывает кнопку `Сохранить`

#### Scenario: Пользователь переключается на другой файл
- **WHEN** текущий файл содержит несохранённые изменения
- **THEN** система сначала сохраняет текущий файл
- **AND** только после этого открывает следующий файл

#### Scenario: Пользователь запускает ключевое действие рабочего экрана
- **WHEN** у задачи есть несохранённые изменения
- **AND** пользователь открывает список задач уровня, запускает проверку, сброс задачи или уточнение
- **THEN** система сначала сохраняет несохранённые файлы

#### Scenario: Пользовательские Tailwind-классы участвуют в preview
- **WHEN** пользовательский файл задачи из `user/` содержит Tailwind-классы
- **THEN** preview-рендер использует CSS для этих классов
- **AND** визуальное оформление не зависит от того, лежал ли класс в versioned `onboarding/tasks/` или был создан уже в `user/`

#### Scenario: Пользователь открывает список задач
- **WHEN** пользователь открывает `/tasks`
- **THEN** система показывает список всех задач
- **AND** сортирует задачи по их коду

#### Scenario: Пользователь работает с задачей в лаборатории
- **WHEN** пользователь находится в рабочем экране задачи
- **THEN** система не показывает техническую подпись вроде `base.png` рядом с preview
- **AND** приоритетно показывает детали конкретной задачи, а не общее описание уровня

### Requirement: У задачи есть канонический path-based маршрут

Система SHALL открывать задачу по path-based адресу, а не через query-параметры экрана.

#### Scenario: Пользователь открывает конкретную задачу
- **WHEN** пользователь открывает `/tasks/<taskId>`
- **THEN** система открывает канонический экран `Component` для этой задачи

#### Scenario: Пользователь открывает внутренний экран задачи
- **WHEN** пользователь открывает `/tasks/<taskId>/<screen>`
- **THEN** система открывает соответствующий экран внутри этой задачи
- **AND** не требует query-параметров для выбора пользовательского экрана

#### Scenario: Пользователь открывает task screen по коду файла
- **WHEN** пользователь открывает `/tasks/<taskId>/<screen>`
- **THEN** значение `screen` совпадает с кодом допустимого для этого уровня файла/экрана

#### Scenario: Пользователь открывает экран перехода к следующему уровню
- **WHEN** пользователь открывает `/tasks/<taskId>/next`
- **THEN** система может перенаправить пользователя на канонический экран задачи `/tasks/<taskId>`
- **AND** не обязана показывать отдельный переходный экран следующего уровня

#### Scenario: Пользователь открывает экран полного завершения задачи
- **WHEN** пользователь открывает `/tasks/<taskId>/done`
- **THEN** система показывает отдельный экран, что задача завершена целиком

#### Scenario: Пользователь открывает экран результата проверки
- **WHEN** пользователь открывает `/tasks/<taskId>/check`
- **THEN** система показывает актуальный одноразовый результат последней проверки уровня этой задачи

#### Scenario: Для уровня нет отдельного task note
- **WHEN** пользователь открывает `/tasks/<taskId>` или `/tasks/<taskId>/<screen>` на уровне, для которого в задаче нет отдельного `tip.md`
- **THEN** система не падает с runtime error
- **AND** показывает пустой текст пояснения задачи

#### Scenario: Для уровня есть отдельный task note
- **WHEN** пользователь открывает `/tasks/<taskId>` или `/tasks/<taskId>/<screen>` на уровне, для которого существует `onboarding/tasks/<taskId>/levels/<levelId>/tip.md`
- **THEN** система показывает этот текст как Markdown-контент

### Requirement: Строка задачи на стартовой странице показывает статус и действия

Система SHALL показывать для каждой задачи в компактной строке:
- название задачи;
- текстовый статус задачи;
- либо кнопку `Начать`, либо текущий номер уровня;
- кнопку `Продолжить`;
- горизонтальный индикатор уровня;
- кнопку `Сбросить задачу`.

#### Scenario: Задача ещё не начиналась
- **WHEN** задача находится в состоянии `Не начиналась`
- **THEN** система показывает текстовый статус `Не начиналась`
- **AND** показывает кнопку `Начать`
- **AND** по нажатию `Начать` открывает задачу на стартовой странице первого уровня

#### Scenario: Задача уже начата
- **WHEN** задача уже имеет текущий уровень
- **THEN** система показывает текущий уровень
- **AND** показывает кнопку `Продолжить`
- **AND** показывает горизонтальный индикатор уровня

### Requirement: Интерфейс задачи поддерживает reset

Система SHALL позволять выполнить reset задачи как со стартовой страницы пользователя, так и со страницы самой задачи.

При reset система SHALL удалить только user-owned рабочие и сгенерённые файлы задачи, не затрагивая project-owned конфиг и референсы.

#### Scenario: Пользователь нажимает `Сбросить` на стартовой странице
- **WHEN** пользователь подтверждает reset задачи из списка задач
- **THEN** система удаляет только user-owned рабочие и сгенерённые файлы
- **AND** не удаляет project-owned файлы `base`, `variants` и `config`
- **AND** показывает задачу как `Не начиналась`

#### Scenario: Пользователь нажимает `Сбросить задачу` на странице задачи
- **WHEN** пользователь подтверждает reset из рабочего экрана задачи
- **THEN** система удаляет только user-owned рабочие и сгенерённые файлы
- **AND** не удаляет project-owned файлы `base`, `variants` и `config`
- **AND** показывает задачу как `Не начиналась`

### Requirement: Экран задачи использует закреплённую нижнюю prompt-полосу

Система SHALL отображать уточняющий prompt composer как нижнюю полосу, закреплённую у нижнего края экрана задачи.
Система SHALL при этом сохранять основную рабочую область максимально широкой и не перегруженной лишними боковыми отступами.

#### Scenario: Пользователь прокручивает содержимое задачи
- **WHEN** основной контент task-экрана становится длиннее высоты viewport
- **THEN** основной контент скроллится
- **AND** нижняя prompt-полоса остаётся закреплённой у нижнего края экрана

#### Scenario: Пользователь открывает экран задачи
- **WHEN** task-экран отрисован
- **THEN** prompt composer визуально отделён от основной области как нижняя полоса на чёрном фоне

#### Scenario: Пользователь открывает task-экран
- **WHEN** task-экран отрисован
- **THEN** основная рабочая область не теряет заметную долю ширины из-за лишних боковых отступов

### Requirement: Prompt composer не участвует в основном scroll-контейнере

Система SHALL отделять prompt composer от основной scrollable области task-экрана.

#### Scenario: Task-экран показывает историю, статусы и composer
- **WHEN** пользователь взаимодействует с экраном задачи
- **THEN** история, статусы и прочий основной контент могут прокручиваться независимо
- **AND** prompt composer остаётся в собственной не-scrollable нижней области

### Requirement: Задание содержит историю промптов пользователя

Система SHALL хранить историю промптов пользователя по заданию в user-owned каталоге `user/` в порядке выполнения.

#### Scenario: Пользователь делает вторую итерацию
- **WHEN** пользователь запускает вторую (и далее) итерацию
- **THEN** система сохраняет новый промпт в историю задания

### Requirement: Onboarding-составляющая задачи приходит из onboarding-репозитория

Система SHALL считать task onboarding-описание, task config и базовые task reference assets частью внешнего onboarding-репозитория.

#### Scenario: Система читает задачу как onboarding-сущность
- **WHEN** системе нужно прочитать onboarding-составляющую задачи
- **THEN** она рассматривает onboarding-репозиторий как канонический источник


## Обязательные части (MVP)

- Минимум одна PNG‑картинка интерфейсного компонента (источник: любой PNG).
- Текущее состояние набора файлов компонента в user-owned workspace (см. `openspec/specs/component-file-set/spec.md`).
- История промптов пользователя в `user/` (см. `openspec/specs/iteration/spec.md`).
- Максимальный уровень задачи `maxLevel` (см. `openspec/specs/task-levels/spec.md`).

## Требования (MVP)

- Набор PNG-картинок обязателен для инициирующего запуска задания.
- Система должна однозначно связывать набор PNG-картинок и набор файлов с одним заданием.
- В рамках задания итерации изменяют состояние набора файлов (и, при необходимости, дописывают историю промптов).
- Каждая задача должна явно хранить `maxLevel`, чтобы система могла ограничить её траекторию по уровням.
