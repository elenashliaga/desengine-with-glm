# Контроль доступа

Контроль доступа описывает allowlist-допуск в защищённую часть продукта и возврат пользователя на целевой маршрут после авторизации.

## Purpose

Зафиксировать поведение allowlist-допуска для path-based пользовательского контура без query-параметра `next`.

## Requirements

### Requirement: Доступ в систему требует актуального allowlist-допуска

Система SHALL считать пользователя допущенным к защищённой части продукта только при наличии актуального allowlist-допуска, не распространяя это требование на публичный корневой маршрут `/`.

#### Scenario: Пользователь открывает защищённую часть системы без допуска
- **WHEN** пользователь пытается открыть защищённый пользовательский маршрут без успешной allowlist-проверки
- **THEN** система переводит его на `/auth`

#### Scenario: Пользователь открывает публичный корень без допуска
- **WHEN** пользователь без допуска открывает `/`
- **THEN** система не переводит его на `/auth`
- **AND** показывает публичную страницу состояния системы

#### Scenario: Пользователь открывает защищённую часть системы с просроченным допуском
- **WHEN** пользователь пытается открыть защищённый пользовательский маршрут
- **AND** локальный allowlist-допуск старше 24 часов с момента успешной проверки
- **THEN** система не считает такой допуск валидным
- **AND** переводит пользователя на `/auth`

### Requirement: Allowlist-допуск требует суточной ревалидации

Система SHALL ограничивать срок действия allowlist-допуска 24 часами с момента последней успешной проверки.

#### Scenario: Допуск ещё свежий
- **WHEN** пользователь уже проходил allowlist-проверку
- **AND** с момента успешной проверки прошло не более 24 часов
- **THEN** система принимает такой допуск как валидный

#### Scenario: Допуск истёк
- **WHEN** пользователь уже проходил allowlist-проверку
- **AND** с момента успешной проверки прошло более 24 часов
- **THEN** система считает допуск истёкшим
- **AND** требует новую allowlist-проверку

### Requirement: Система различает отсутствие допуска и истечение допуска

Система SHALL различать состояния “допуск отсутствует” и “допуск истёк” в пользовательском и диагностическом контурах.

#### Scenario: Пользователь видит страницу допуска после истечения доступа
- **WHEN** пользователь возвращён на `/auth` из-за просроченного допуска
- **THEN** система может явно сообщить, что предыдущий допуск истёк и требуется повторная проверка

#### Scenario: Диагностический экран показывает состояние допуска
- **WHEN** система отображает статус allowlist-допуска
- **THEN** она различает состояния “допуск уже выдан”, “допуск ещё не выдан” и “допуск истёк”

### Requirement: После допуска пользователь возвращается на целевой path

Система SHALL возвращать пользователя после успешного допуска на тот path, который он пытался открыть, без использования query-параметра `next`.

#### Scenario: Пользователь шёл на защищённый экран задачи
- **WHEN** пользователь без допуска пытается открыть path внутри защищённой части продукта
- **THEN** система сохраняет целевой path вне финального пользовательского URL
- **AND** запись возвратного path выполняется в route handler, а не во время SSR-рендера страницы
- **AND** после успешного допуска возвращает пользователя именно на этот path

#### Scenario: Возвратный path невалиден
- **WHEN** сохранённый path отсутствует, повреждён или не относится к разрешённым пользовательским маршрутам
- **THEN** после успешного допуска система открывает безопасный канонический маршрут по умолчанию

### Requirement: Проверка allowlist устойчива к хостингам без корректного HEAD

Система SHALL уметь подтверждать allowlist-маркер даже на тех статических хостингах, где `HEAD` работает нестандартно или отклоняется.

#### Scenario: Хранилище не подтверждает marker через HEAD, но отдаёт его через GET
- **WHEN** система проверяет наличие allowlist-маркера по email
- **AND** запрос `HEAD` возвращает неожиданный код вместо канонических `200` или `404`
- **THEN** система повторяет проверку через `GET`
- **AND** принимает `200` как успешный допуск

### Requirement: Локальный production-start не требует HTTPS для сессионных cookie

Система SHALL уметь работать через `npm run start` на `http://localhost` без потери allowlist-сессии из-за флага `secure`.

#### Scenario: Локальный запуск через next start на localhost
- **WHEN** приложение запущено локально без HTTPS
- **AND** пользователь успешно проходит allowlist-проверку
- **THEN** система сохраняет access-cookie и cookie возвратного path без обязательного `secure`
- **AND** пользователь может открыть защищённую часть продукта в этом локальном запуске
