# Навигация

Навигация определяет официальный публичный URL-контракт продукта и карту пользовательских entry point'ов.

## Purpose

Зафиксировать человекочитаемые path-based адреса продукта и убрать query-driven пользовательскую навигацию из официального контура.

## Requirements

### Requirement: Продукт имеет фиксированную top-level карту пользовательских URL

Система SHALL предоставлять пользователю следующие канонические top-level адреса:
- `/`
- `/tasks`
- `/levels`
- `/auth`
- `/config`
- `/help`

#### Scenario: Пользователь ориентируется в основных разделах продукта
- **WHEN** пользователь открывает или копирует основной адрес продукта
- **THEN** top-level URL отражают структуру разделов продукта без скрытых экранов в query-параметрах

### Requirement: Корневой маршрут сейчас явно переводит пользователя на список задач

Система SHALL использовать `/` как явную точку входа, которая на текущем этапе перенаправляет пользователя на `/tasks`.

#### Scenario: Пользователь открывает корень продукта
- **WHEN** пользователь открывает `/`
- **THEN** система явно переводит его на `/tasks`

### Requirement: Пользовательские URL не используют query-параметры как официальный контракт

Система SHALL не использовать адреса вида `?param=1&q=2` как часть официальной пользовательской навигации.

#### Scenario: Пользователь переходит по публичной ссылке на экран продукта
- **WHEN** пользователь открывает человекоориентированный URL продукта
- **THEN** адрес кодирует экран через path-сегменты
- **AND** не требует query-параметров для определения пользовательского экрана

### Requirement: Переход между уровнями имеет отдельный path внутри задачи

Система SHALL использовать отдельный маршрут `/tasks/<taskId>/next` для экрана перехода между уровнями одной и той же задачи.

#### Scenario: Пользователь завершил текущий уровень задачи
- **WHEN** пользователь попадает на экран перехода к следующему уровню
- **THEN** система открывает канонический адрес `/tasks/<taskId>/next`

### Requirement: Страницы config и help существуют как отдельные top-level маршруты

Система SHALL предоставлять отдельные top-level страницы `/config` и `/help`.

#### Scenario: Пользователь открывает страницу конфигурации
- **WHEN** пользователь открывает `/config`
- **THEN** система показывает страницу конфигурации и статусов подключения

#### Scenario: Пользователь открывает страницу помощи
- **WHEN** пользователь открывает `/help`
- **THEN** система показывает отдельную страницу помощи
